## 一、目标与验收口径

本需求增加“先定位 UP 主，再从其公开视频投稿中选择下载”的一次性工作流，同时保留现有直接视频链接/编号下载和管理员视频关键词搜索。定位只帮助发现作品，不建立 UP 主白名单，也不改变现有单个视频下载授权边界。

交付后的用户可观察行为如下。

### 管理员

- 搜索页保留现有“视频关键词”模式，新增“UP 主”模式。
- 可按 UP 主名称搜索候选，也可直接输入精确 UID 或 `https://space.bilibili.com/<UID>` 主页链接。
- 名称搜索每页 20 个候选，只展示并让管理员选择，不按重名或相似度自动确认身份。
- 候选卡展示头像、名称、UID、简介、粉丝数和公开投稿数；选中后读取该 UP 主资料和第一页投稿，不再要求第二次确认。
- 投稿浏览保留媒体库/设备目标、分组、标签、最低清晰度和单项目标档位能力；单个多分 P 投稿仍以整个 BV 为选择与下载单位。
- 管理员一次最多选择 100 个作品；不得提供“选中该 UP 主全部投稿”。

### 普通网站用户

- 导航仍只有“下载”和“任务”，不开放搜索页，也不开放 UP 主名称搜索。
- 下载页内部提供“视频链接/编号”和“UP 主投稿”两个模式；两边草稿相互独立，并在同一网站登录会话内离开页面后继续保留。
- “UP 主投稿”只接受精确正整数 UID 或规范的 Bilibili UP 主主页 HTTPS 链接。主页路径后的子路径、查询串和片段可忽略；名称、任意关键词、短链、跳转链接、非 `space.bilibili.com` 主机、用户信息和非默认端口一律拒绝。
- 可以定位任意存在的 UID，不需要管理员预先加入名单；现有直接提交任意有效 BV、av、ep、ss 或受支持视频 URL 的能力保持不变。
- 下载目标固定为当前设备，不接收媒体库、分组、标签或强制替换参数。
- 画质固定为自动选择当前 Bilibili 登录可用的最高档；最低清晰度使用管理员配置的全局门槛，普通用户只能查看，不能通过请求覆盖，也不能设置单项目标档位。画质预览只读展示可用档位。
- 可选择数量等于 `10 - 本人当前活动任务数`，最小为 0；服务端提交时重新计算，页面上的旧数字不构成配额承诺。
- 本人待领取设备导出在下载页顶部集中提示并提供“领取文件”；同作品在领取、过期或放弃前不能重复创建任务。

### 共同投稿浏览行为

- 只包含 UP 主公开的视频投稿，不包含动态、专栏、音频、直播或收藏夹。
- 每次读取一个 Bilibili 原始页，每页 20 条；投稿排序只提供“最新发布”和“播放最多”。
- 标题“不筛选/精准/模糊”只在浏览器当前已取回页执行，分别表示原始结果、包含全部拆分词、包含任意拆分词。
- 默认隐藏已下载；管理员同时默认隐藏已删除。关闭隐藏后允许显式选择，并在提交前分别确认重新下载或重新下载曾删除作品。
- 排队中、下载中和待领取作品不可选择；失败、取消、过期和没有本地记录的作品可重新选择。
- 跨页选择只属于当前搜索上下文。翻页、排序和标题筛选不清除选择；更换关键词、UP 主或搜索模式时，如已有选择则站内确认后清空。
- 管理员搜索页的关键词与 UP 主模式共用同一套投稿卡、筛选、选择和续页规则；普通用户只使用精确 UP 主上下文。

## 四、冻结的领域与状态规则

### 身份和作品

- UP 主身份的唯一键为规范十进制 UID；名称只用于管理员候选查找和展示。
- 投稿唯一键为 BV 号。多分 P 的标题、预览和下载仍进入现有整 BV 链路。
- 解析主页链接时由服务端重新校验 scheme、hostname、userinfo、port 和路径，前端校验只负责即时提示。
- UP 主不存在、存在但无公开视频、资料存在但投稿不可访问三种结果必须分别呈现；不得用同名 UP 主替代。

### 本地状态优先级

同一作品同时命中多个事实时，展示和候选判断按以下优先级收敛：

1. 本人待领取设备导出；
2. 本人排队中或下载中的任务；
3. 已下载；
4. 管理员可见的已删除；
5. 本人最近失败、取消或过期；
6. 未下载。

活动任务和待领取状态始终禁止选择。已下载与已删除只有在用户显式关闭默认隐藏后可选，并分别确认；其他终态不阻止重试。普通用户的所有状态查询必须按 `owner_user_id` 限定，管理员的“已下载”只由共享媒体库有效文件证明。

内部状态映射中，设备任务已经 `success` 且导出仍为 `preparing` 或 `ready` 时统一呈现为“待领取”；任务尚未成功时仍按活动/失败状态呈现。活动与待领取冲突只按当前认证拥有者判断，管理员能够查看他人任务不等于他人任务会阻止管理员选择。

### 设备下载事实

- 普通用户的浏览器完整消费无 Range 的 GET 响应并收到全部字节时，才建立设备下载事实；HEAD、响应未读完、连接中断、任务成功或仅生成可领取文件都不能建立。
- 同一用户同一作品再次完整领取时，将持久事实更新时间推进到新的、可证明的领取时间；同一任务的清理重试保持第一次完整领取的时间不变。
- 该事实只影响本人筛选，不返回给其他普通用户，也不改变管理员的媒体库下载定义。

## 五、Bilibili 适配、API 与权限合同

### 上游读取

在 `app/search.py` 内复用现有 Cookie 读取、WBI 签名、密钥缓存、HTML 清理和 HTTP 客户端边界，增加三个聚焦函数，不预建通用爬虫框架：

- 按名称读取 UP 主候选：调用现有 WBI 搜索入口的 `bili_user` 类型；
- 按 UID 读取资料：读取 UID、名称、头像、简介、粉丝数、投稿数；
- 按 UID、排序和页码读取公开视频投稿：每次请求 20 条并映射为现有下载元数据。

没有服务器 Bilibili 登录时先尝试公开读取。WBI 签名错误清除对应 Cookie 指纹的密钥并只重试一次；风控、登录失效、网络错误和上游格式异常停止当前续页，不做无限重试。

服务端 3 分钟原始缓存键必须包含读取模式、规范关键词或 UID、排序、页码和 Bilibili Cookie 指纹。缓存值只含 Bilibili 原始规范数据，不得混入网站用户、媒体库、任务、标签或设备下载事实；角色与所有者状态在每次响应时重新装饰。“刷新”只逐出当前原始页。

定位、名称查询、翻页和筛选不写服务端最近记录、收藏或业务审计；只有用户实际提交下载任务后沿用现有下载审计。

### HTTP 入口

| 方法与路径 | 角色 | 作用 |
| --- | --- | --- |
| `GET /api/search` | 仅管理员 | 保留视频关键词搜索；增加当前下载目标参数，以便返回该目标下的权威候选状态 |
| `GET /api/bilibili/creators/search` | 仅管理员 | 按名称和页码返回 20 个 UP 主候选 |
| `GET /api/bilibili/creators/resolve` | 管理员、普通用户 | 解析精确 UID/主页链接，读取资料并连同第一页投稿返回 |
| `GET /api/bilibili/creators/{uid}/submissions` | 管理员、普通用户 | 按最新或播放量读取一个投稿页；支持仅刷新本页 |
| `POST /api/download/selection` | 管理员、普通用户 | 新的严格选择批量提交；任一冲突、配额或持久化失败时创建零任务 |

普通用户中间件只按 HTTP 方法和完整路径/数字 UID 路径模式放行后三个必要入口，不对白名单使用宽泛的 `/api/bilibili/creators/` 前缀；`creators/search` 和现有 `/api/search` 的 403 行为必须有回归测试。所有写请求继续执行现有 CSRF 校验。

### 稳定响应字段

UP 主资料统一返回：

```text
uid, name, avatar, bio, followers, submission_count, profile_url
```

UP 主候选使用同一字段子集。投稿原始字段统一返回：

```text
bvid, title, author, cover, play, duration, duration_seconds, pubdate, url
```

响应根同时返回当前 `page`、`pages`、`total`、固定 `page_size=20`、排序、是否命中原始缓存，以及角色化限制：自动续页最多 10 页、管理员选择上限 100，或普通用户活动任务数与剩余名额。

普通用户投稿装饰只允许本人安全状态、本人关联任务 ID、领取时间和可选择原因；不得包含文件路径、媒体库分组、标签、删除历史、其他用户 ID 或上游内部错误。管理员响应继续提供现有标签、媒体库分组、画质和删除状态。

### 安全错误码

路由把上游异常映射为稳定且可操作的安全码：

```text
invalid_creator_locator
creator_not_found
creator_no_public_videos
creator_inaccessible
bilibili_login_required
bilibili_risk_control
bilibili_unavailable
```

“无公开视频”可带已确认的 UP 主资料返回空状态；不存在使用 404；暂时不可访问使用可重试错误。普通用户响应不得包含 Cookie、WBI key、签名参数、原始上游消息、堆栈或服务器路径，详细诊断只进入既有脱敏日志。

## 六、自动续页与会话内状态

续页由浏览器逐页驱动，服务端单次 API 永远只取一个 Bilibili 页面。统一纯策略按以下顺序执行：

1. 读取用户请求的起始页；
2. 用当前标题模式、标题词和本地状态筛选计算可下载候选；
3. 如果至少一个候选存在，立即停止并显示该页，不为凑满 20 条合并后页；
4. 如果候选为零且仍有后页，顺序读取下一页；
5. 遇到自然末页、用户停止、请求取消、上游失败或本轮累计 10 页时停止；
6. 命中 10 页上限时显示已检查区间、跳过页数/作品数和“从下一页继续”；失败时记录失败页并让“重试”从同一页开始。

旧的“成功后推测性预载下一页”退出当前行为合同，避免已经找到候选后仍产生上游请求。浏览器可以命中同网站会话内 24 项 LRU，但缓存命中仍计入本轮检查页数。

标题输入只立即重算当前页，不在每次按键时联网。当前页因此变空时，用户点击“查找后续匹配”或在标题框按 Enter 才启动续页。

每个进行中的扫描使用独立 `AbortController` 和递增 generation。新搜索、更换 UP 主、更换模式、离开路由、退出登录、身份变化或点击停止都会取消旧扫描；旧响应不得覆盖新上下文。上游失败时保留已选作品、当前缓存、已检查范围和失败页。

浏览器状态按当前认证用户隔离并只保存在内存：

- 管理员视频关键词上下文和已选 UP 主上下文各自明确；切换上下文时按规则确认并清空选择。
- 普通用户直接下载草稿与 UP 主投稿草稿独立；在同一会话内切换页面仍保留。
- 排序、翻页和标题筛选不改变上下文，选择以 BV 去重。
- 投稿列表是实时分页而非快照；新增或删除投稿导致页间移动是允许行为，当前页只由显式刷新更新。
- 退出、认证失效或换账号统一清空草稿、选择、缓存和扫描状态。

## 七、严格批量任务创建

新的 `/api/download/selection` 只服务搜索/投稿卡片的单项或批量选择，保留现有 `/api/download` 作为直接输入入口，避免把旧调用者的“已存在则跳过”语义悄然改掉。管理员现有关键词搜索卡片也切换到严格入口。

严格入口在同一个发布边界内完成：

1. 从认证会话确定拥有者和角色，重新规范化所有目标并按 BV 去重；
2. 普通用户覆盖目标为设备、最低门槛为全局配置、目标档位为空，并计算实时剩余活动名额；管理员仍接受已授权下载选项；
3. 在对应队列锁内收集整批活动重复、已有有效媒体且未确认重下、本人待领取导出、全局队列容量和本人配额；
4. 任一项失败时不建立队列任务、任务记录、导出记录或日志，返回每个输入项的稳定原因与最新安全状态；容量不足时整批项目都标记为批次容量不足，不任意截取前 N 项；
5. 全部通过后先在一个 SQLite 事务中写入整批正式任务记录，设备目标同时写入整批导出记录；事务成功后才把全部任务一起发布到内存队列并唤醒 worker；
6. 发布前持久化失败则发布零任务；发布阶段的异常执行精确补偿并不得留下部分可见批次。

队列严格路径不得沿用当前的 `active-duplicate -> skipped` 分支。并发提交同一拥有者同一 BV 时最多一个批次成功；不同普通用户仍可同时设备导出同一 BV。失败响应沿用 `ApiError.payload` 让前端合并逐项状态并保留选择，用户修正后可原批重试。

## 八、SQLite v5 与设备导出领取

### 新表

数据库 schema 从 v4 升到 v5，新增最小事实表：

```sql
CREATE TABLE device_download_history(
  owner_user_id TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  source_key TEXT NOT NULL,
  downloaded_at REAL NOT NULL,
  PRIMARY KEY(owner_user_id, source_key)
);
```

只记录角色为普通用户的完整设备领取。按一批 BV 查询时使用拥有者与主键前缀，不扫描其他用户记录。

### 消除模糊清理状态

`exports` 增加 `cleanup_target_state TEXT NOT NULL DEFAULT ''`。完整传输、放弃和过期共享文件清理实现，但不能共享事实语义：

```text
完整发送全部字节
  -> 事务内首次写 exports.downloaded_at
  -> upsert device_download_history（同作品取较新证明时间）
  -> 尝试清理
     -> 成功：state=downloaded
     -> 失败：state=cleanup_pending, cleanup_target_state=downloaded

放弃或过期
  -> 不写领取时间和历史
  -> 尝试清理
     -> 成功：state=discarded/expired
     -> 失败：state=cleanup_pending, cleanup_target_state=原目标
```

后台重试只负责再次清理并进入 `cleanup_target_state`，不得再次制造领取事件。旧库中已有但没有目标的 `cleanup_pending` 无法证明来源，迁移后按保守的非领取清理目标处理，绝不回填设备下载事实。

### 迁移与回填

- 沿用现有 SQLite 一致性检查、迁移前 backup、`BEGIN IMMEDIATE`、整体回滚、schema version 和外键检查。
- 只从 `exports.downloaded_at IS NOT NULL`、拥有者存在且角色为普通用户、`source_key` 非空的记录按拥有者与作品聚合回填；同作品采用最新的已证明时间。
- `ready`、`preparing`、传输中断、空拥有者、无效拥有者、空作品键和旧的模糊 `cleanup_pending` 均保持未知。
- 设备下载事实不随任务历史、导出记录或任务日志清理；删除网站用户时由外键级联删除其事实。
- schema 降级不在应用内实现；需要回滚产品代码时停止应用并恢复自动生成的 v4 迁移前备份。

## 十、验证设计

### 聚焦行为

- 定位符：纯 UID、规范主页 URL、尾随路径/查询/片段成功；零、负数、名称、短链、HTTP、伪造子域、userinfo、异常端口和跳转输入失败。
- 上游映射：名称候选每页 20、重名不自动选择、资料字段、投稿最新/播放排序、BV 去重、整 BV 多分 P、空投稿、不可访问和不存在分别映射。
- 缓存与失败：Cookie 指纹隔离、3 分钟 TTL、当前页刷新、角色装饰不入原始缓存、WBI 失效只重试一次、风控/网络失败停止在准确页且安全错误不泄密。
- 权限：普通用户可调用精确 resolve/submissions 和严格批量入口；名称搜索、现有搜索页和管理员 API 仍为 403；响应不存在全局媒体库、标签、他人任务或路径。
- 候选状态：管理员媒体库定义与普通用户设备事实定义分离；活动/待领取优先阻止；已下载默认隐藏但可确认重下；失败、取消、过期可选；不同普通用户互不影响。
- 批量原子性：混合活动冲突、待领取冲突、媒体库冲突、配额不足、队列满、持久化注入失败和同 BV 并发提交均为零部分创建；成功批次所有任务先持久化再一起可见。
- 领取事实：完整 GET 建立记录；HEAD、中断和未读完不建立；清理失败仍立即建立且重试不改第一次领取时间；放弃/过期清理失败永不建立；再次完整领取推进时间。
- 迁移：v4 备份、v5 表/列、严格回填、未知保持未知、失败整体回滚、外键检查和新版本拒绝降级。
- 前端纯策略：上下文切换、跨页 BV 去重、动态普通用户上限、标题本地过滤、用户触发后续匹配、找到即停、自然末页、10 页上限、继续页、停止、失败同页重试和 generation 防旧响应。
- 浏览器：管理员两种搜索模式、重名候选选择、普通用户无搜索导航、下载页双草稿、只读最高画质、待领取提示、批量错误保留选择，以及既有五档视口无横向滚动和无控件重叠。

### 执行门槛

1. 新增与受影响的 Python/Node 聚焦测试；
2. `python -B -X utf8 SoftwareTesting/doc_consistency/test_doc_consistency.py`；

## 十一、完成条件与停止条件

只有同时满足以下条件，待办才可退出活动区：

- 第一节全部角色行为可由自动测试或明确用户验收证明；
- 普通用户数据隔离、严格批量零部分创建、领取事实时点和 v4→v5 回滚测试通过；
- T-DOC 与经授权的 T-PROJECT full 得到 `passed`，没有必需阶段跳过；归档变更后的 T-ARCHIVE 通过；
- 当前需求、设计、字段契约和更新日志已同步，旧“成功后预载下一页”“普通用户可选最低清晰度”等被替代事实不再冒充当前行为；
- 没有 Cookie、Token、真实用户数据、原始上游响应、测试下载物或仓库外路径进入仓库；
- 用户要求的实施和验收已经完成，方案按生命周期精确归档，待办入口移除。

遇到以下任一情况立即停在当前安全状态并请求授权或新决定：

- 需要使用服务器现有 Bilibili 登录、真实用户数据、真实下载、全量测试、安装依赖、发布、commit、push 或 PR，但尚无明确授权；
- Bilibili 当前响应无法可靠区分不存在、无投稿和不可访问，或需要换用会扩大内容范围/权限的上游入口；
- 严格批量无法在现有队列与 SQLite 边界内证明零部分创建，必须改变既有直接下载合同；
- 发现目标文件有与本需求重叠的用户未提交修改，或迁移需要删除无法证明来源的数据；
- 新决定会开放普通用户名称搜索、跨用户状态、订阅/自动下载或其他本方案排除能力。

## 十二、方案 Review 结论

本次 review 对照当前实现逐项反推后，已将四个容易造成“界面看起来完成、事实却不成立”的问题收进必做路径：

1. 自动续页替代旧的成功后预载，确保找到候选即停止上游请求；
2. 批量原子性下沉到队列发布与 SQLite 持久化之间，而不是只在路由前做一次易竞态检查；
3. 浏览器完整发送事件先建立下载事实，文件清理成为独立、可重试的后续动作；
4. 用 `cleanup_target_state` 消除现有 `cleanup_pending` 的领取/放弃歧义，旧模糊记录不被误判为已下载。

其余方案与现有消费者一致：普通用户不增加搜索路由，管理员复用搜索页，直接下载入口保留，原始 Bilibili 缓存与身份状态分层，跨页选择仍以 BV 为单位。当前没有未决产品选择；Bilibili 非稳定上游和跨队列并发风险均已由稳定错误、原子发布边界及相应回归承接。
