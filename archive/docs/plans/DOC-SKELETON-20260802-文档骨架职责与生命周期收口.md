## 1. 目标与完成条件

目标：

1. 使需求、设计、字段契约及条件专题具有唯一、可解释的当前职责；
2. 使根用户入口只承担简介、最短使用、构建交付及文档和测试总入口；
3. 为当前、兼容、临时和历史材料建立明确归属、退出条件及当前承接；
4. 使项目 T-DOC 与当前标准资产的生命周期和导航规则一致；
5. 使命令、文件修改、Git、安装、发布和自动化副作用具有无冲突的长期授权入口。

完成条件：

- 每份活动文档都有唯一职责、活动入口和适用的退出条件，同类事实不再存在并列权威入口；

- 完成、取消、暂缓或被替代时，本方案退出活动入口和 `docs/方案/`。

## 3. 已裁决差异

### 3.1 当前事实职责如何唯一承接

- 目标规则：核心文件各自承接需求、设计和字段事实；其他专题必须职责独立、长期有效、有活动入口和退出条件。
- 可选处理 A：按标准职责拆分兼容正文并收口到三个核心文件，独立专题只保留不可替代的专题职责。
- 可选处理 B：暂时保留兼容路由，但先为每份现有专题写明唯一职责、当前承接关系和退出条件，再由独立内容一致性任务逐步拆分正文。
- 可选处理 C：保持现状。
- 推荐理由：推荐 B 作为低风险第一步；它先消除结构歧义，不在骨架施工中替用户做大规模正文语义裁决。
- 用户决定：选择 A。三个核心文件分别成为用户可观察行为、实现结构和字段规则的唯一当前真源；`docs/产品需求与架构基线.md`、`docs/账号权限与会话管理.md` 和 `docs/任务所有权与保留策略.md` 只作为迁移材料，完成事实拆分与入口更新后作为 V0.6 历史专题归档。详见 [ADR 0001](../../../docs/adr/0001-current-facts-by-type.md)。

### 3.2 根用户入口如何收敛

- 目标规则：根 README 只保留文档和测试总入口，不重复专题清单。
- 可选处理 A：删除根 README 的专题枚举，只保留 `docs/README.md`、`SoftwareTesting/README.md` 及确有必要的非专题用户入口。
- 可选处理 B：保留当前重复清单。
- 推荐理由：推荐 A；专题仍可从文档索引在一至两跳内到达，不降低可达性。
- 用户决定：选择 D1。只移除根 README 中与 `docs/README.md` 重复的“文档”专题清单，改为文档与测试总入口；实际 QNAP、备份和使用场景中的上下文链接继续保留。

### 3.3 已完成版本材料如何退出活动区

- 目标规则：已完成批次、Review、动态结果和被替代方案属于历史材料；继续活动的兼容手册必须有独立职责和退出条件。
- 可选处理 A：将七份候选全部判为历史，在当前事实完成承接后归档。
- 可选处理 B：逐份裁决；保留仍承担当前兼容验收职责的文档并补充退出条件，其余归档。
- 可选处理 C：保持现状。
- 推荐理由：推荐 B；V0.6.2 的部分兼容规则仍由当前测试和 workflow 使用，不能只凭版本号机械归档。
- 用户决定：选择 A，并明确 V0.6.2 命名的测试或 workflow 只是兼容回归标识，不延长版本文档的活动生命周期。七份候选均在当前事实完成承接后归档；`docs/releases/V0.7.0.md` 必须先解除 workflow 的机械引用。当前事实由三个核心真源承接，版本历史由 `CHANGELOG.md` 和归档承接。详见 [ADR 0001](../../../docs/adr/0001-current-facts-by-type.md)。

### 3.4 项目门禁采用哪一实现

- 目标规则：标准路线的两个 T-DOC 源码从当前 Skill 资产逐字节安装，发现目标内容不同必须先展示冲突并由用户决定。
- 可选处理 A：在施工阶段把两个目标源码替换为当前通用资产，不制作项目分叉。
- 可选处理 B：保留当前项目门禁，并把项目改按等价既有治理重新证明全部结构职责和必要安全结果。
- 推荐理由：推荐 A；项目已经采用标准骨架，当前差异正是通用规则演进，不存在已证明必要的项目特例。
- 用户决定：选择 A（E1）。项目保留标准骨架路线；施工时将两个目标 T-DOC 源码逐字节替换为当前 `project-doc-skeleton` 标准资产，不建立项目分叉。

### 3.5 push 与自动发布如何保持分别授权

- 目标规则：commit、push、PR 和发布分别授权，默认接线不得让一种授权隐式扩大为另一种。
- 可选处理 A：保留自动化，但在长期规则中明确任何会触发发布的 `main` push 必须同时取得 push 与发布两项授权，并在执行前展示副作用。
- 可选处理 B：把 GHCR 和 Release 发布入口改为显式手动触发，使普通 `main` push 不直接发布。
- 可选处理 C：保持现状且不补充授权说明。
- 推荐理由：若维护者希望保留现有自动发布体验，推荐 A；若要求两项操作在时间上也可独立执行，选择 B。
- 用户决定：不采用 A，也不只采用手动发布版本的 B，而是停止未来全部正式发布。项目不再自动或手动创建新的版本 tag、GitHub Release 或 GHCR 正式镜像；现有远端发布物保留。版本专用发布 workflow 退出活动 workflows 并归档，Docker workflow 仅保留无 GHCR 登录、无 `packages: write`、`push: false` 的构建验证，同时移除 tag 触发和手动发布输入。此前关于手动发布入口的 H1 已撤回，发布说明来源 J1 不再适用。详见 [ADR 0002](../../../docs/adr/0002-source-push-does-not-publish.md)。

### 3.6 命令、安装、删除与归档如何分别授权

- 用户决定（G1）：FastCtx 文件读取、搜索和查找不算命令；任何 Shell、Git、构建、测试或产品命令均须明确授权，安装和删除分别授权，不能由命令或施工授权推定。
- 用户决定（I1）：文件在仓库内移动或重命名到归档位置，只要内容完整保留并同步更新引用，就按文件修改授权处理；只有内容被丢弃且仓库内没有等价保留副本时，才需要单独的删除授权。
- Review 后补充决定：Docker 新部署默认设置 `BUILD_LOCAL=true` 并使用本地镜像名；既有 `.env` 不覆盖，现有用户由文档提示手动切换。既有 V0.7.0 GHCR 镜像仅作为冻结历史后备。
