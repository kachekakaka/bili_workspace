## 1. 目标与范围

### 1.1 目标

1. 修复概览页作品卡无法进入对应作品详情的问题。
2. 修复 UP 主投稿返回 HTTP 图片地址时被前端替换为占位图的问题。
3. 为管理员增加“UP 主全量入库”：后台遍历单一 UP 主的全部公开视频投稿，并在不挤占手工提交的前提下持续补充媒体库下载任务。
4. 在 UP 主页面和任务中心提供可解释的作业进度、取消、失败续查和本次运行期结果。

### 1.2 不纳入

- 不向普通网站用户开放，不支持设备导出。
- 不建立未来新投稿订阅、定时扫描或自动化任务。
- 不持久化全量入库作业，不修改 SQLite schema；服务重启后由管理员重新发起。
- 不强制重新下载媒体库已有投稿，不恢复删除历史中的投稿。
- 不改变现有最多 100 项、全有或全无的手工批量下载提交。
- 不访问真实 Bilibili 账号或真实用户数据进行测试。
- 不覆盖 `dist/` 中的 Windows 打包快照或 `launcher/current-build.json`，不提交、不推送、不发布。

## 2. 用户可观察合同

### 2.1 概览与封面

- 概览页作品卡提供明确的鼠标和键盘入口；激活后进入作品库并直接打开该作品的详情与播放界面，不要求作品恰好位于当前作品库分页。
- 跨页只传递一次性作品 ID，不改变地址栏路由合同，也不覆盖现有作品库查询、分组等一次性跳转条件。
- Bilibili 返回的协议相对图片地址和 `http://` 图片地址统一规范为 HTTPS；最终展示仍经过现有受信图片域名与前端安全回退。

### 2.2 UP 主全量入库

- 入口只在管理员的 UP 主浏览且下载目标为媒体库时显示；设备导出和普通用户页面不显示，后端也必须拒绝越权请求。
- 每次作业绑定一个 UID、发起管理员、目标分组和最低清晰度；标题筛选及页面排序不进入作业范围。
- 作业以发起时间为投稿截止点，固定按发布时间倒序发现；后续发布的投稿不属于本次作业。
- 发起前展示 UP 主、投稿总数估计、目标分组、最低清晰度、一次性范围与跳过规则，并要求二次确认。
- 媒体库已有、存在活动任务或已有删除历史的投稿分别计数并跳过；既有失败或已取消任务不阻止新任务。
- 下载队列接受投稿或投稿被明确分类后，作业即完成该投稿；作业不等待对应下载任务成功或失败。
- 同一时间只有一个作业执行发现和入队，其余不同 UID 作业依次等待；相同 UID 已经活动或等待时，重复发起返回现有作业而不重复创建。
- 取消等待作业会将其移出等待序列；取消活动作业只停止后续发现和入队，已经创建的下载任务继续由任务中心管理。

### 2.3 完成与失败

- 预期结果分为已入队、媒体库已有、活动任务、删除历史；这些跳过不算失败。
- 单条投稿解析或任务创建失败时记录安全原因并继续，其余投稿不受影响；遍历结束后作业为“部分完成”。
- 分页读取使用有限、可取消的重试；仍失败时停在原页，不跳过未知投稿，并允许在当前服务运行期从该页继续。
- 本次运行期内可只重试尚未入队的单条失败项；下载任务进入队列后的执行失败仍使用任务中心既有重试能力。
- 作业完成表示所有已发现候选均已入队或明确分类，不表示下载任务均已完成。

## 3. 实现设计

### 3.1 概览到作品详情

- 为概览作品卡增加明确作品 ID、按钮语义和 Enter/Space 键盘行为。
- 点击后通过独立 `sessionStorage` 一次性键传递媒体 ID并进入作品库；作品库读取后立即清除该键，完成当前页加载后直接调用既有详情打开能力。
- 详情读取继续使用按媒体 ID 的服务端接口，因此不依赖当前作品库筛选或分页。

### 3.2 图片 URL 规范化

- 收敛 `app/search.py` 的图片规范化函数，让 `//host/path` 和 `http://host/path` 产生 `https://host/path`，原有 HTTPS 保持不变。
- 视频关键词结果、UP 主资料和 UP 主投稿共用同一规则；路由层继续只放行受支持的 HTTPS 图片域名，浏览器继续对加载失败使用占位图。
- 增加 HTTP 投稿封面、协议相对封面、HTTPS 原值和非法值的回归覆盖。

### 3.3 当前运行期作业管理器

- 新增由 `AppState` 拥有的全量入库管理器；内部只保存当前运行期状态，不写数据库。应用停止时先停止管理器，再停止下载队列，避免关停期间继续创建任务。
- 管理器使用一个协调线程和等待序列；保留最近 20 个当前运行期结果。相同 UID 的开始请求幂等返回活动或等待作业。
- 作业状态至少区分 `waiting`、`discovering`、`enqueuing`、`stopping`、`completed`、`partial`、`failed`、`cancelled`，并提供阶段、页码、总数估计、发现数、入队数、各类跳过数和安全失败摘要。
- 发现阶段捕获发起时间作为截止点，强制使用 `pubdate`，按 BV 去重并过滤截止点之后的投稿。若遍历期间上游总数或页数发生变化，从第一页做有界稳定性复核；不能获得一次稳定遍历时按分页失败处理，不虚报全部发现完成。
- 入队前重新检查媒体库、活动任务和删除历史，避免发现阶段后的状态变化。实际创建使用单投稿严格校验，使并发冲突只分类当前投稿，不产生代表预期跳过的伪任务记录。
- 全量入库创建的活动任务窗口不超过当前下载并发数；窗口有空位时才补充下一项，因此手工提交最多只会排在少量已创建任务之后。队列容量暂时不足属于等待条件，不记作投稿失败。
- 单条异常隔离并脱敏；分页重试、容量等待和停止等待均可被取消，不用无限重试或不可中断固定休眠掩盖错误。

### 3.4 HTTP API 与权限

- 增加管理员专用的开始、列表/详情、取消、失败页继续和失败项重试接口；所有写接口沿用现有 Cookie 会话与 CSRF 校验。
- 开始请求只接收 UID、`group_id` 和最低清晰度，下载目标在服务端固定为媒体库，拥有者只取当前认证会话；客户端提交的名称、总数、目标或拥有者不作为可信事实。
- 服务端重新验证 UID、分组、清晰度和当前 Bilibili 登录可读性；响应和审计只记录安全标识与统计，不记录 Cookie、完整凭据或文件系统路径。
- 普通用户请求按既有权限边界拒绝；前端隐藏按钮不作为安全措施。

### 3.5 前端状态与操作

- `submission-browser.mjs` 在管理员媒体库目标下增加全量入库按钮、确认弹窗和当前 UID 作业卡；切换到设备导出时隐藏入口。
- `tasks-impl.mjs` 为管理员增加独立的“全量入库作业”区域，展示活动、等待及最近结果；该区域不把作业伪装成下载任务。
- 两个页面只在挂载期间读取作业状态，离开页面不影响后端作业；恢复页面后以服务端当前运行期状态为准。
- 活动作业可取消，分页失败可继续，部分完成可重试未入队失败项；所有按钮应防重复提交并显示服务端返回的实际状态。

### 3.6 文档与兼容边界

- 更新需求文档、设计文档、字段契约和必要测试说明，区分“批量下载提交”“UP 主全量入库”“全量入库作业”。
- 现有手工选择、跨页选择、正常用户设备导出、任务 SSE 和下载任务生命周期保持原合同。
- 不新增数据库迁移、配置字段、环境变量、依赖或外部服务。

- 管理员全量入库的权限、一次性范围、跳过、串行、低优先级、取消、失败继续和当前运行期边界均由自动化测试证明。

- 长期需求、设计、字段契约与实现一致；活动方案按文档生命周期归档，待办从活动入口移除。
- 不覆盖现有 Windows 打包快照，不触碰真实配置、Cookie、数据库、媒体或其他未归属改动。

遇到以下任一情况停止并请求差额授权或新决策：

- 实现需要持久化作业、数据库迁移、普通用户或设备导出支持、未来投稿订阅，或改变现有严格批量提交合同。

- 上游分页无法在有界复核内稳定、完整测试或候选 EXE 验证失败，且修复需要改变已确认语义。
