# 轻量计划与测试证据治理方案

- 待办 ID：`DOC-GOV-20260827`
- 当前状态：已完成
- 实施边界：本次只修改仓库内治理文档、门禁与隔离证据工具；未清理既有仓库外证据、未修改外部 Skill、未运行全量测试，也未执行 Git 写操作。

## 目标与范围

在不增加大型治理总文档的前提下，把容易导致实施变慢或偏航的规则放回现有单一真源，并只对稳定、可机械判断的部分增加门禁：

1. 采用“缺少哪项授权，只询问哪项”的协作方式，避免机械重复确认。
2. 为低风险任务提供只存在于对话中的轻量方案路径，缩减正式活动方案的固定内容。
3. 将活动文档门禁与归档完整性门禁分开，避免无关历史问题阻塞普通全量测试。
4. 约束测试选择和复跑经济性，禁止用无意义的大规模输入证明可由小夹具直接构造的边界。
5. 为仓库外测试证据建立短期保留、只读规划和精确删除机制。

不修改产品语义、领域语言、设计文档常量或发布策略；不新增 `GOVERNANCE.md`、`CONTEXT.md` 条目或 ADR。

## 决策基线

### 授权与方案路径

- 只读检查、审查或讨论产生修改建议时，在首次写入前询问尚缺的保存或实施授权。
- 用户已经明确要求修改、修复、实施或写代码时，在确定范围内直接继续，不重复询问同一授权。
- 方案保存与实施是独立授权，但用户可以在同一条指令中同时授予；commit、push、全量测试和其他升级动作仍按项目协作约束单独判断。
- 局部、低风险、无需长期交接的任务只在对话中说明目标、影响范围、最小验证和停止条件，不登记待办、不保存方案、不归档。
- 用户明确要求保存，或任务存在未决产品/安全语义、破坏性或外部状态风险、需要分阶段长期交接和恢复时，才建立正式活动方案；文件数量和跨模块本身不构成触发条件。

正式方案生命周期调整为：

| 待办状态 | 活动方案数量 | 含义 |
| --- | --- | --- |
| `待确认` | 0 或 1 | 尚有未决问题；用户明确要求时可以保存一份草案 |
| `待实施` | 恰好 1 | 方案已经定稿，但尚未开始施工 |
| `实施中` | 恰好 1 | 已取得实施授权并正在施工 |
| `暂缓` | 0 | 活动方案退出活动目录，待办保留暂缓事实 |

正式方案的最小内容为目标与范围、授权边界与排除项、最小验证、完成与停止条件。依赖、联合复核、交接、回滚等字段仅在实际存在时添加，不再要求逐项填写固定九项收尾模板或用“不适用”占位。

### 活动文档与归档门禁

- `T-DOC` 保持 `full`，默认只检查活动 Markdown、固定入口、活动待办/方案和测试 Registry；不枚举归档正文，也不检查归档正文与索引的一一登记。
- 新增 `T-ARCHIVE`，登记为 `affected_only`。本项一旦被选择，就完整检查 `archive/docs` 与 `archive/SoftwareTesting` 的索引格式、正文唯一登记和当前承接关系。
- 修改归档正文或索引、关闭并归档活动方案，或重命名/删除归档索引引用的当前 Markdown 时选择 `T-ARCHIVE`；普通产品全量测试不因未受影响的归档问题选择本项。
- 项目内门禁脚本是本项目执行真源。外部文档骨架 Skill 只可作为另一个任务的输入，其优化、同步和发布不属于本方案，也不得以外部文件哈希相等覆盖项目内适配。
- 门禁性能通过隔离夹具证明忽略目录和归档正文不进入活动扫描；不设置易受机器负载影响的固定秒数阈值。

### 验证经济性

- 普通验证只选择能够证明当前影响范围的最小集合。
- 只有规模、吞吐或性能本身是被测性质时，才使用规模/负载输入；计数边界优先用小配置或小夹具直接构造。
- 只有结构化证据能够核验相同候选、输入、测试契约和相关环境，且仍在有效期内时，才不机械重复同一证明；对话中的历史结论不能单独替代验证。候选、测试契约、输入、相关环境或证据有效性变化后重新判断。
- 可机械判断的规则进入夹具；需要语义判断的规则由对应长期文档承接，不用脆弱的文本数量或耗时门禁代替。

### 测试证据生命周期

- `passed` 和 `not_run` 原始运行证据在最终结果更新时间达到 72 小时后可删除。
- `failed`、`blocked` 和 `inconclusive` 原始运行证据在最终结果更新时间达到 7 天后可删除。
- 所有原始证据均有期限；活动方案或长期文档的引用不得延长期限，需要长期保留时只提炼命令、候选身份、结果和必要结论。
- 在 `tools/t_project_isolation.py` 增加只读 `gc-plan` 和精确 `gc-apply`。规划只读取测试根直接子目录的所有权标记和结果，不递归统计内容；输出精确 `run-id`、分类、关键身份哈希和计划摘要，不写计划文件。
- 新运行的初始结果明确为未终结，最终记录写入 `finalized_at`。有终态证明的运行按普通期限进入候选；既有或异常运行缺少终态证明时，达到 7 天后只能进入单独的 `legacy_or_abandoned` 精确候选，不得混入普通候选。
- `gc-apply` 必须同时接收逐项明确的 `run-id`、候选分类和预期计划摘要，重新构建同一计划并验证测试根、仓库身份、运行 schema、Registry ID、结果身份、终态/遗留分类、期限、直接子目录和重解析点边界；任何漂移整体拒绝，不接受 glob、前缀、测试根或未知目录。
- `legacy_or_abandoned` 候选必须在 dry-run 中明确说明缺少终态证明，并由用户对精确清单另行确认；它们不会被永久保护，也不会自动删除。
- 普通测试和任务收尾不静默调用删除。现有仓库外证据不在本方案实施范围内；实际清理必须先展示新的精确 dry-run，再取得相应删除授权。
