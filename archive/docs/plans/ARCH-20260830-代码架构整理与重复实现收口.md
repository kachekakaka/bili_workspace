## 目标与范围

本方案只收口三条已经由代码证据确认的问题链：HTTP 路由依赖注册顺序决定权威实现，任务生命周期由基础队列、所有权子类和运行时扩展共同修改，SQLite schema、迁移、连接与跨领域事务分散在多层继承和独立 Store 中。完成后，每项现有能力只有一条运行路径和一个明确职责所有者。

范围包括后端路由组合、任务队列及快照、认证与作品库相关 SQLite 持久化、作品删除编排、相应前端调用契约、行为测试和长期文档。实施采用可独立验证的切片；每个切片在替代路径可用且受影响验证通过后立即删除旧路径，不保留永久双实现。

本方案不是全项目分层重写，也不以文件行数、模块数量或风格统一为目标。BBDown 下载算法、搜索算法、浏览器页面结构、Windows 启动器、Docker 交付和正式发布策略不在范围内。

## 已确认合同

1. 保留需求文档声明的用户行为、仓库前端实际使用的 API、schema v4 数据和当前受支持的旧库迁移。内部模块名、类继承、被注册顺序遮蔽的处理器及没有消费者的实现不承担兼容义务。
2. 每个 HTTP 方法与路径只有一个权威处理器。任务列表查询正式使用 `q`、`sort`、`direction`，同步修正字段契约，不增加 `keyword`、`sort_by`、`sort_dir` 别名。
3. 暂停、继续、取消的状态与阶段组合保持现有合同。所有终态任务都可原 ID 重试；重试保留拥有者和最初 `created_at`，清空上次执行状态、结果和日志，只保留最新一次执行。
4. schema 版本保持 v4。迁移前一致性备份、单事务迁移、外键检查、失败关闭、未来 schema 拒绝降级和最近三份备份继续有效。
5. 单个作品只有在所选文件操作和逻辑删除完整完成后才算成功；失败不得提交逻辑删除或报告成功。批量删除以单个作品为提交单位，逐项返回成功与失败。

## 目标职责

| 职责所有者 | 唯一职责 | 明确不承担 |
| --- | --- | --- |
| API 组合根与领域 Router | 注册账号、系统、任务、作品库四类现行端点，并统一认证和响应辅助逻辑 | 通过 include 顺序覆盖同签名端点 |
| `TaskQueue` | 任务身份、拥有者、源标识、排队与全部生命周期转换、快照通知 | 外部函数修改私有锁、容器或替换内部方法 |
| 具体 `Database` 单元 | 唯一拥有 SQLite 连接、PRAGMA、schema、迁移、备份、显式事务与关闭 | ORM、可替换数据源接口、通用 Repository 框架 |
| 认证、任务、作品库、标签、删除记录 Store | 通过组合使用同一个 `Database`，只执行各自领域读写，并能加入调用方已经开启的事务 | 自建连接、自建 schema、继承聚合 Store、嵌套提交 |
| 作品库协调服务 | 协调 IndexStore、媒体文件和上述具体 Store 的用例顺序 | 假装文件系统与 SQLite 可以整批事务回滚 |

`AppState` 显式持有这些具体对象并负责构造和关闭；Router 只依赖其用例所需对象。不会为依赖注入、未来数据库或未知消费者再增加接口层。

## 实施切片

### 1. 路由权威收口

- 建立一个 API 组合入口和账号、系统、任务、作品库四个领域 Router；把当前实际生效的处理器及必要辅助逻辑迁入对应职责。
- 保留前端实际调用的 `/api` 与 `/api/enhancements` 路径、请求响应字段、状态码、权限隐藏规则和流式响应；不保留仅被遮蔽的历史处理器。
- 在运行时组合后的路由表上验证 HTTP 方法与路径唯一，并以关键成功、权限拒绝和失败响应证明行为；不建立固定路由数量或源码位置快照。
- 迁移完成后删除 `app/api.py`、`app/task_ownership_api.py`、`app/enhancement_api.py`、`app/refinement_api.py` 和 `app/catalog_overrides.py` 中已被替代的路由路径；若某模块仍承接非路由职责，先把该职责迁到已有明确所有者再删除模块。

退出条件：应用启动后不存在重复方法/路径，现有前端调用和 API 行为测试通过，`main.py` 不再依赖 Router 注册先后来选择实现。

### 2. 任务生命周期归一

- 让任务对象直接持有不可变拥有者、公开源标识和必要的内部存储标识，消除线程局部所有权上下文及平行字典。
- 由 `TaskQueue` 的公开方法唯一实现创建、暂停、继续、取消、原 ID 重试、删除、清理、列表和所有者过滤；每次转换由同一入口在队列锁下原子校验并更新，随后通过唯一有序机制持久化快照和发布变更，不让多个层分别修改状态，也不把外部 I/O 强制绑在队列锁内。
- 原 ID 重试适用于成功、跳过、失败、取消和暂停终态，保留最初 `created_at`，只重置本次执行字段和日志；管理员操作不改变原拥有者。
- 删除 `OwnedTaskQueue` 的覆盖层和 `task_extensions` 的 monkey patch；API、后台工作线程和持久化回调不再直接操作队列私有容器或替换私有方法。

退出条件：两条下载队列共用同一生命周期实现，重启快照恢复、所有权隔离、活动上限、暂停/取消竞争、原 ID 重试和 SSE 通知行为通过受影响测试，旧扩展路径已经删除。

### 3. SQLite 连接、schema 与迁移归一

- 引入一个具体 `Database`，集中现有连接配置、SQL 函数、完整 v4 schema、迁移前备份、迁移事务、外键检查、未来版本拒绝和关闭逻辑。
- 先让标签和删除记录 Store 改为接收该 `Database`，把它们当前自行执行的建表与旧“不要”标签迁移并入唯一 schema/迁移入口；现行 v4 数据库启动时仍幂等应用完整 v4 schema 和一次性兼容整理，兼容已存在或尚未建立这些后加表的 v4 数据库。随后让其余持久化代码共享同一连接和事务。
- 保持 schema v4 的表、字段、索引和数据可读，不为本次代码重组升级版本。若实现证明必须变更持久化字段或版本，触发停止条件重新决策。

退出条件：生产构造链只有 `Database` 打开和关闭 SQLite，全部 schema 与迁移只有一个入口；空库、现行 v4、受支持旧库、损坏库、未来版本库和迁移失败行为通过相应测试。

### 4. 持久化领域改为组合

- 将认证/用户/会话、任务快照/设备导出、分组/作品/进度/转码、标签和删除记录分别移入具体领域 Store；并发认证操作继续在明确事务边界内串行化。
- 作品库协调服务负责 IndexStore、文件操作、转码和多个 Store 的用例编排；Router 不再调用 Store 私有 SQL 帮助方法。
- `AppState` 改为显式构造和持有具体 `Database`、Store、协调服务与队列；后台清理只由对应数据所有者执行。
- 替代完成后删除 `NasStore`、`SerializedAuthNasStore`、`TaskOwnershipNasStore`、`MigrationSafeTaskOwnershipNasStore` 的继承链及只为该继承链存在的模块，不建立兼容外观。

退出条件：认证、任务、设备导出、分组、作品库、标签、观看进度和删除记录均通过现有公开入口工作，代码中不再存在聚合 Store 继承或领域 Store 自建 SQLite 连接。

### 5. 作品删除失败语义收口

- 单个作品删除先解析真实媒体与所选文件范围，并在本次调用内保留足以恢复索引的原条目；要求删除文件时，文件阶段完整完成后，才由作品库协调服务开启一个 SQLite 事务，让媒体、标签和删除记录 Store 加入该事务并一起提交。
- 文件阶段部分失败时不提交 SQLite 逻辑删除，刷新 IndexStore 与数据库可观察状态并返回该作品失败；已经实际删除的文件不伪装成可回滚，用户可对保留的作品记录重试。
- SQLite 提交失败时同样不报告成功，并用本次调用保存的条目恢复或按实际文件重建可重试的 IndexStore 状态；这个恢复信息不持久化为 journal。批量入口对去重后的每个作品独立执行，返回逐项成功和错误，不因一项失败停止其余项。
- 覆盖保留文件、删除文件、文件中途失败、数据库事务失败、重复请求和混合批次；不为无法实现的跨资源原子回滚增加 journal 或补偿框架。

退出条件：任何响应中的成功项都已完整满足本次删除选择，失败项仍有可重试且与实际文件一致的作品状态，搜索删除标识和重新下载清除标识行为没有回归。

### 6. 文档、死代码与生命周期收尾

- 每个切片同步更新直接受影响的需求、设计和字段契约；最终核对 Router、任务状态、SQLite 数据流、删除语义与实际代码一致。
- 删除只验证旧模块名、继承形状、固定源码文本或被遮蔽行为的测试；缺失的真实行为先由最小边界测试承接，不创建版本镜像、文件数量、源码 Token、覆盖率百分比或机器耗时门槛。
- 完成条件与验证满足后，从活动待办移除 `ARCH-20260830`，把本方案移动到 `archive/docs/plans/` 并登记两个归档索引，再运行关闭后的文档门禁。

## 实施结果（2026-08-31）

- 已完成四个领域 Router 的权威收口，组合后 66 个现行方法/路径无重复；旧路由覆盖模块和被遮蔽处理器已删除。
- 已由单一 `TaskQueue` 承接任务身份、所有权、生命周期、同 ID 重试、快照通知和 SSE 变化发布；所有权子类、私有状态扩展和 monkey patch 已删除。
- 已由一个具体 `Database` 统一 SQLite 连接、完整 v4 schema、迁移、备份和事务，账号、任务、作品库、标签与删除记录 Store 通过组合共享；聚合 Store 继承链已删除。
- 已由 `LibraryService` 按单个作品协调索引、文件、媒体、标签和删除历史，覆盖保留文件、部分文件失败、数据库失败、重复请求和批量混合结果。
- 普通核心回归曾暴露 Windows 子进程解码未显式使用 UTF-8，以及测试助手把总耗时当成任务完成门槛；两处测试基础设施已按真实输出编码和可观察进展修正。最终候选的源码边界、compileall、Ruff、291 项非浏览器 Python 行为测试、全部前端语法、40 项 Node 行为测试、T-DOC、Markdown 链接检查和 `git diff --check` 均已通过。
- 经用户单独授权，最终 T-PROJECT full 已通过规范入口，覆盖完整 Python、Ruff、Node 与隔离 Playwright；本次仓库外隔离运行目录由入口成功精确清理。待办和方案已按完成条件关闭，不涉及 commit、push、PR、发布或正式认证。

## 完成条件

1. 运行时不存在重复 HTTP 方法/路径，现行前端 API 与权限行为保持可用，任务筛选字段统一为 `q`、`sort`、`direction`。
2. 任务生命周期、所有权、快照和通知由一个 `TaskQueue` 实现，所有终态原 ID 重试符合已确认语义，旧覆盖层与 monkey patch 已删除。
3. 一个具体 `Database` 唯一拥有 SQLite 连接、schema、迁移和事务；具体领域 Store 通过组合共享它，schema v4 数据与支持迁移通过验证。
4. 单个与批量作品删除准确遵守完整成功、逐项提交和失败可重试语义，不再吞掉标签或删除记录失败后报告成功。
5. 被替代路由和 Store 继承链退出生产路径，剩余测试只保护真实行为、合同和失败边界，长期文档与实现一致。
6. 所有切片聚焦验证通过，最终 T-PROJECT full、T-DOC 和受影响的 T-ARCHIVE 得到可判定结果；未运行项没有被描述为通过。
