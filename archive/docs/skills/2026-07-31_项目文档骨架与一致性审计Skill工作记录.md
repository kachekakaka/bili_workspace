## 5. project-doc-consistency 执行记录

### 5.1 模式与范围

- 模式：`check`
- 范围：全量静态内容审计
- 文档：37 份活动 Markdown；10 份归档按历史时间语境处理
- 证据：代码、配置、Windows/Docker 脚本、GitHub Actions、测试契约和运行资产清单
- 未执行：联网、GitHub 状态查询、产品运行、真实数据操作和发布

### 5.2 明确不一致

1. `SECURITY.md` 仍声明维护版本为 V0.5.x，当前应用版本为 0.7.0。
2. 缺少 Node.js 时，`verify.bat` 和源码自检会跳过必需前端检查却仍报告完整成功，与测试协议冲突。
3. Windows 运行时构建工作流直接 commit 并 push `main`，与项目 PR/授权纪律冲突。
4. 旧 `release-v062.yml` 仍会在当前 `main` CI 完成后触发，却强制断言版本为 0.6.2。
5. V0.7 验收写“tag 触发 Docker 镜像”，实际流程是发布工作流显式 dispatch。
6. 当前发布前验证清单遗漏独立 T-DOC。
7. Windows 恢复文档先运行阻塞式 `start.bat`、后运行 `verify.bat`，顺序不合理。

### 5.3 需要决策

1. 新核心文档与既有“产品需求与架构基线”等文档仍存在兼容期职责重叠，无法只凭代码决定如何拆分正文。
2. T-PROJECT 规范命令当时内嵌 T-DOC，但 Registry 又要求全量测试分别运行两个 `full` 项，职责发生重复。

### 5.4 无法静态验证

- GitHub 上实际 CI、tag、Release 与 GHCR 镜像状态。
- 外部 Git Bundle、Windows 恢复包、校验文件和验证报告是否已经保存。
- 历史“门禁全绿”“原地升级通过”等动态结果是否绑定同一候选 SHA。

## 6. 用户确认与最终取舍

### 6.1 Node.js 与验证入口

用户指出 Node.js 是开发工具，不是应用运行依赖。最终确定：

- `verify.bat` 是 Windows 部署自检；不运行 T-DOC。
- 普通部署允许没有 Node.js，但必须明确显示前端开发检查未执行，不能声称完整发布验证通过。
- 发布严格模式通过 `BILI_VERIFY_REQUIRE_NODE=1` 要求 Node.js，缺失时阻断。
- Linux/macOS 的 T-PROJECT 是开发源码完整自检，Node.js 为前置条件。
- T-DOC 独立运行；T-PROJECT 不重复执行文档门禁。

### 6.2 Git 与自动化

用户明确表示是否推送通常由本人决定，因此未采用“机器人自动创建 PR”的建议。最终确定：

- Windows 运行时工作流只构建、验证并上传 Artifact。
- 工作流使用 `contents: read`，不 commit、不 push、不创建 PR。
- 是否把生成的运行包纳入仓库，由用户另行决定。
- 删除过期的 V0.6.2 发布工作流。

### 6.3 文档语义范围

- 本次只修复直接证据充分的冲突。
- 保留需求、设计、字段契约与既有事实文档的兼容路由状态。
- 不在本次任务中做大规模正文拆分、合并或 ADR 裁决。

### 6.4 确认方式调整

用户最初要求逐项确认，随后指出：代码和文档能够直接确定的事项不应反问，只询问无法唯一判断的事项。

这与两个 Skill 的理想行为一致，但实际交互前段仍产生了过多逐项确认。后续应把确认限定为：

- 会改变职责或实现方向的真实取舍；
- 不可恢复的结构动作；
- Git、发布、真实数据等新增授权；
- 证据无法唯一确定的语义决定。

## 9. 两个 Skill 的有效点

### 9.1 project-doc-skeleton

- 把结构、事实、语义决定分开，避免骨架初始化顺手重写产品事实。
- 固定入口、两跳可达性、归档唯一登记和 Registry 关系能够稳定约束文档增长。
- 明确修改、命令、commit、push、PR、发布分别授权，避免授权扩张。
- 通用门禁资产逐字节复制并配正反夹具，降低项目内分叉风险。
- 归档不再作为当前事实入口，历史快照得以保留。

### 9.2 project-doc-consistency

- “一致、不一致、无法验证、需要决策、未覆盖”五类结论能防止把证据不足误写成错误。
- 能区分规则真源、当前描述事实、历史记录和动态验证结果。
- 通过代码、配置、工作流和测试交叉核对，发现了单看 Markdown 无法发现的自动化问题。
- 对归档使用时间语境，没有因旧版本名称和行为自动判错。

## 10. 建议优化 project-doc-skeleton

1. **先给现有命令分类再接入测试治理。** 对每个既有入口明确标记“用户运行、部署自检、开发自检、CI、正式认证”。不得因名称包含 `verify` 就把 T-DOC 注入用户部署入口。
2. **建立依赖角色表。** 分别记录生产依赖、开发依赖、发布依赖和可选工具，并把 skip、blocked、failed、inconclusive 与具体入口绑定。
3. **迁移路径影响扫描应覆盖所有文本入口。** 文档移动后搜索代码、测试、工作流和脚本中的旧路径；仅运行少量聚焦测试时必须明确剩余风险。
4. **验证结论分层。** 分开报告“机械骨架通过”“聚焦项目测试通过”“完整 T-PROJECT 未运行”，避免用户把前两者理解为整仓通过。
5. **为已有部署入口增加保护夹具。** 当项目声明某入口面向最终用户时，骨架初始化不得自动加入文档、Node 或其他开发依赖。
6. **确认策略更严格地执行证据优先。** 能调查的事实集中调查；互不依赖的规则集中确认；只把真实取舍逐项交给用户。
7. **工作树换行策略纳入迁移检查。** Windows `.bat` 应保持 CRLF，活动 Markdown 保持 LF；补丁后在完整测试前先做字节级检查。

## 11. 建议优化 project-doc-consistency

1. **把“文档修订”和“实现修复”分开输出。** `sync` 只能改现有文档；发现脚本或工作流违反文档契约时，应生成明确的普通实现任务交接，而不是让用户误以为 sync 会改代码。
2. **增加命令角色一致性检查。** 对部署入口、开发入口、CI 和正式认证分别检查依赖、skip 语义和成功文案。
3. **增加发布自动化专项检查。** 检查活动旧版本 workflow、直接写 `main`、`[skip ci]`、tag 与候选 SHA 绑定、隐式 tag 触发和显式 dispatch 是否相符。
4. **先处理可证明项，再询问决策项。** 报告可按“直接修复、需要用户决定、外部动态无法验证”三组交付，避免逐条询问已经有唯一证据的事实。
5. **明确显式复盘文档例外。** 默认 check 不持久化报告是合理的；若用户明确要求为 Skill 优化保留执行复盘，可允许交给骨架 Skill 归档，并标明它不是当前项目真源。
6. **在全量审计中输出验证债务。** 对未运行的产品、网络、CI 和外部交付事实形成单独清单，不阻塞直接证据充分的修复。

## 12. 建议增加的 Skill 回归场景

- 现有 `verify.bat` 是部署入口，Node.js 不是运行依赖，T-DOC 必须保持独立。
- 同一个工具在本地部署可选、在发布认证必需，结果语义必须不同。
- 文档从 `docs/plans` 迁移到 `archive/docs/plans`，但未纳入聚焦集合的测试仍引用旧路径。
- 旧版本发布 workflow 在当前版本继续自动触发。
- 构建 workflow 拥有 `contents: write` 并直接 push `main`，但项目规则要求用户决定 Git 写入。
- 用户先要求逐项确认，随后要求只询问无法确定的事项；Skill 应及时收敛确认范围。
- 用户显式要求保存 Skill 执行复盘；审计 Skill 不直接持久化，由骨架 Skill 放入归档并登记。
- Windows 批处理补丁产生混合 CRLF/LF，机械检查应在完整测试前发现。
