## 2. 完成的骨架工作

### 2.1 首次建立标准骨架

- 建立根级协作约束、活动文档总入口、需求、设计、待办、测试 Registry 和字段契约入口。
- 建立 `SoftwareTesting/` 测试治理主干、T-DOC 门禁及其正反规则夹具。
- 将运维材料收口到 `docs/运维/`，把已完成方案和历史发布材料迁移到 `archive/docs/` 并统一登记。
- 保留既有产品事实正文，通过兼容入口路由，没有在首次结构迁移中擅自裁决正文语义。

### 2.2 完成职责与生命周期收口

- 需求、设计和字段契约成为按事实类型划分的唯一当前真源，兼容期聚合文档退出活动区。
- 根 README 收敛为用户入口、构建交付入口及文档和测试总入口，不再复制专题导航。
- 已完成版本、Review、问题清单和发布材料在当前事实完成承接后归档。
- 待办、活动方案、完成记录和空条件目录按生命周期退出，归档索引保持唯一登记。
- T-DOC 更新为当前标准资产，项目内两份门禁源码与 Skill 资产逐字节一致。
- Git、命令、安装、删除、发布及自动化副作用的授权边界得到长期承接。
- 项目明确停止未来正式发布；活动 workflow 不再创建版本 tag、GitHub Release 或推送 GHCR 正式镜像。

## 3. 关键裁决

1. 采用标准骨架，而不是把当前项目重新证明为等价但非标准的既有治理。
2. 当前事实按需求、设计、字段类型分别承接，不继续保留聚合文档作为并列真源。
3. 已完成版本材料退出活动区；测试和 workflow 中的版本名称只作为兼容标识，不延长版本文档生命周期。
4. 通用机械门禁采用当前 Skill 资产，不维护项目分叉。
5. 文件修改、命令、安装、commit、push、PR、发布和删除分别授权，不相互推定。
6. 停止未来正式发布；普通源码 push 不隐式扩大为发布授权。

这些结果只绑定当时的候选状态，不代表此后仓库变更自动通过，也不证明产品事实、测试充分性或全项目安全。

## 5. 骨架 Skill 的有效机制

- 把结构治理与产品事实同步分开，避免初始化骨架时顺手重写业务语义。
- 先建立承接和入口，再移动或退出旧材料，历史正文没有因结构整理而丢失。
- 使用检查、保存方案、施工和生命周期关闭的分离停点，授权范围能够被观察和复核。
- 通过活动入口、两跳可达性、归档唯一登记和机械门禁限制文档无序增长。
- 对通用资产采用逐字节安装和冲突停点，能够发现 Skill 资产演进与项目副本漂移。
- 将普通验证、全量测试、正式认证及 `not_run` 分开，避免把局部通过描述成整仓认证。

## 6. 暂不阻塞定型的回归增强

骨架 Skill 的主体流程已经可用，可以进入稳定观察期。下列事项适合作为后续小型回归增强，不要求再次改造整体职责：

1. 生命周期关闭或最终交付前，再执行一次通用资产逐字节比较，避免只依赖施工中途结果。
2. 对既有命令先区分用户运行、部署自检、开发自检、CI 和正式认证，防止向部署入口注入文档或 Node.js 等开发依赖。
3. 文档迁移后明确检查引用、配置、工作流、脚本和测试中的旧路径，并准确报告未运行完整测试留下的范围。
4. 修改 Windows 批处理文件时增加 CRLF 检查；活动 Markdown 继续保持 UTF-8 与 LF。
5. 把“事实调查问题”“真实语义取舍”和“写入、命令、Git 等授权问题”分别处理；能够由当前证据确定的事实不交给用户反复确认。

## 7. 阶段结论

`bili_workspace` 的标准文档骨架、职责入口、历史生命周期、测试治理结构和发布授权边界已经完成收口。骨架 Skill 不再是当前优先改造对象；后续以真实项目回归观察为主，只在上述防回归场景再次出现时做针对性修订。

下一阶段的主要优化对象是 `project-doc-consistency`：重点检查它如何冻结内容范围、区分直接事实与真实决策、处理实现交接，以及避免把普通内容审计扩张成无边界的测试、CI 或安全审计。
