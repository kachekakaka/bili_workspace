# 测试协议

## 验证层级

- 普通验证是默认层级，只运行能够证明本次影响范围的最小充分集合。
- 全量测试运行 Registry 中全部 `full` 项、本轮受影响的 `affected_only` 项和用户明确加入的 `explicit` 项。
- 正式认证在全量测试之外形成候选、范围、结果和未覆盖项的正式交接；它不自动授权 tag、Release、push 或发布。

测试以行为、合同和失败边界为单位选择。同一候选、环境和性质只证明一次；CI job、文件名或历史版本不同不构成新增测试职责。只有规模、吞吐或性能本身是被测性质时才使用规模输入或耗时门槛；固定正文、文件数量、目录形状、源码 Token、覆盖率百分比和机器耗时不能替代行为判断。

## 核心回归与影响扩展

每次产品代码变化至少运行以下快速核心回归：

1. `product-validation` 对应的完整非 `integration`、非 `playwright` Python 行为测试；
2. `frontend` 对应的全部 JavaScript 语法检查和 Node 行为测试。

模块专属测试按影响追加。认证、持久化、任务队列、公共 API 或前端公共运行时变化，以及影响无法可靠界定时，扩大到现有 Playwright 阶段并形成 T-PROJECT full。Docker、Windows 启动器和归档门禁仍按各自 `affected_only` 条件选择，不能用 Python 静态检查代替真实平台验证。

核心回归不创建新的 Registry ID、pytest marker、固定用例清单或版本测试文件。新增或修改行为覆盖关键成功路径、合理失败路径和跨模块边界；没有真实消费者的兼容层或防御分支不为“以后可能用到”而增加测试。

不稳定测试先复现根因并修复竞态、状态泄漏、错误等待或隔离问题。根因位于产品代码或缺失外部环境时，准确记录 `failed` 或 `blocked`；未经决定不得用重试、延长固定等待、永久跳过或降低断言改变结果。

## Registry 与结果

Registry 只登记真正独立的套件、触发条件和入口，不登记 CI 并行阶段或每次运行。T-DOC 与 T-PROJECT 是 `full`；T-ARCHIVE、T-DOCKER、T-LAUNCHER 和 T-BILIBILI-LIVE 在其输入受影响时选择。T-PROJECT 不重复运行 T-DOC，Playwright 是其 full 的必需阶段。

`T-BILIBILI-LIVE` 在有效仓库本地授权（或逐次显式授权）、固定场景和安全本地环境存在时先运行快速运行器检查，再运行本次影响域的真实成功链，最后才运行相关模拟测试。真实链的 `failed`、`blocked` 或 `inconclusive` 会停止后续昂贵阶段；外部登录、网络、风控、浏览器、工具或磁盘不足为 `blocked`，产品合同错误为 `failed`，兼容结构漂移或上限前无下载完成为 `inconclusive`。普通 pytest、T-PROJECT 与 CI 永不自动选择它。

- `passed`：所有必需阶段均执行并得到可判定成功结果。
- `failed`：测试已进入可判定阶段，断言、收集、静态检查或产品行为失败。
- `blocked`：依赖、运行时、授权或环境不足，测试未进入可判定阶段。
- `inconclusive`：执行中断、运行器异常或必需阶段被跳过。
- `not_run`：没有执行。

退出码为零但必需阶段被跳过时仍是 `inconclusive`。输入、候选、测试合同或相关环境变化后重新判断影响，不以对话中的旧结论替代当前验证。

## 交接

实施前和最终报告记录测试层级、验证影响域、实际命令、结果和未覆盖项。普通运行结果由控制台和 CI Artifact 承接，不建立仓库外长期 schema、保留期或 GC 协议；需要长期保存时，只在方案或交接中提炼必要结论，不引用原始运行目录作为永久真源。
