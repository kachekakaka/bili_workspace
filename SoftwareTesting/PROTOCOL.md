# 测试协议

## 验证层级

- 普通验证是默认层级，只运行能够证明本次影响范围的最小测试集合。
- 全量测试必须运行 Registry 中全部 `full` 项、本轮受影响的 `affected_only` 项和用户明确加入的 `explicit` 项。
- 正式认证必须先完成候选影响所需的全量测试，核对已执行证据绑定同一候选身份，并形成记录候选身份、实际范围、逐项结果、未覆盖项和授权边界的结构化交接；认证不自动授权 tag、Release、push 或发布。

构建义务不自动提升验证层级。当前项目的全量测试至少包含 `T-DOC` 和 `T-PROJECT`；两项分别执行，`T-PROJECT` 不重复运行文档门禁。T-DOCKER 是 `affected_only` 项，只在 Docker、运行依赖或镜像输入受影响时选择。T-PROJECT full 内部必须完成源码、Python、Node 和 Playwright 阶段，CI 为并行执行保留的浏览器作业仍属于 T-PROJECT，不形成新的 Registry 项。

## 结果语义

- `passed`：所有必需项都已执行并得到可判定的成功证据。
- `failed`：测试已进入可判定阶段，断言、静态检查、收集或项目行为失败。
- `blocked`：运行前置条件、运行时或依赖不足，测试没有进入可判定阶段。
- `inconclusive`：执行被中断、运行器异常，或必需项被跳过而证据不完整。
- `not_run`：没有执行。

退出码为零但存在必需项或 T-PROJECT 必需阶段跳过时，结果仍为 `inconclusive`，不能补成 `passed`。严格入口缺少 Node、Playwright 包或可用浏览器且尚未进入检查阶段时为 `blocked`。输入、测试契约或候选身份变化后重新判断受影响范围。

## 任务交接

每次实施前和最终报告都记录测试层级、验证影响域与具体验证项。全量测试和正式认证的摘要保存在仓库外，并绑定候选身份、实际范围、逐项结果、未覆盖项和授权边界。

仓库外测试根只证明项目和路径所有权，可以容纳多个 Registry 测试项；每个运行目录只能归属一个测试项。新建 `.bili-workspace-test-run.json` 与 `results/result.json` 使用 schema v2，并以必填 `test_id` 绑定活动 Registry ID；创建、校验和记录结果时身份必须一致。既有 schema v1 运行只按旧语义解释为隐式 `T-PROJECT`，记录时保留 v1 结构，不得静默迁移或绑定到其他测试项。未知 schema、缺失身份、非法 ID 或身份不匹配均拒绝处理。
