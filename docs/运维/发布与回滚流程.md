# 源码更新、验证与回滚流程

## 1. 停止正式发布后的边界

源码以普通 Git 文件直接存在于 `main`，禁止通过压缩分片、Base64 或运行时恢复源码。项目停止未来正式发布：源码 push、PR、合并和普通 CI 都不得创建新版本 tag、GitHub Release，也不得推送或更新 GHCR 正式镜像。

活动自动化只允许：

- 检查源码结构、编译、静态规则、测试和前端语法；
- 构建但不推送 Docker amd64/arm64 镜像；
- 上传有保留期限的短期验证产物。

既有 `v0.7.0` tag、GitHub Release 和 GHCR 镜像保留为冻结历史状态，不代表后续 `main`。恢复任何正式发布能力都必须先形成新的显式决策，并分别取得修改与发布授权。

## 2. 源码验证

完整源码验证入口由测试治理文档定义。当前 Linux/macOS 聚焦命令包括：

```bash
python -B -X utf8 SoftwareTesting/doc_consistency/test_doc_consistency.py --workspace-root .
python tools/verify_source.py
python -m compileall -q app tests tools docker
python -m ruff check --no-cache app tests tools docker
python -m pytest -q -p no:cacheprovider
find web -type f \( -name '*.js' -o -name '*.mjs' \) -print0 | sort -z | xargs -0 -n1 node --check
node --test tests/frontend/*.test.mjs
```

普通验证是默认层级；全量测试和正式认证只在用户明确选择后执行。具体执行授权与高风险边界以[项目协作约束](../../AGENTS.md#授权与安全)为准。

相关验证还覆盖五档 Playwright 视口、Windows `verify.bat`、Docker 本地构建、数据库迁移/回滚、持久化、权限、Markdown 内部链接和敏感信息边界。

## 3. Windows 源码更新

在现有源码目录手动执行：

```bat
git pull --ff-only origin main
verify.bat
start.bat
```

`verify.bat` 准备仓库内便携运行时，并运行 Python、Ruff、pytest 和运行资产冒烟；检测到 Node.js 时追加 `.js/.mjs` 语法与 Node tests。需要强制 Node 检查时设置 `BILI_VERIFY_REQUIRE_NODE=1`。实际配置、数据库、媒体和解压目录不会被快进更新覆盖。

## 4. Docker 源码构建与更新

新部署的 `docker/.env.default` 使用：

```env
BILI_IMAGE=bili-workspace:local
BUILD_LOCAL=true
PULL_IMAGE=true
```

更新：

```bash
git pull --ff-only origin main
./docker/build-and-start.sh
```

脚本从当前检出源码执行 `docker compose build --pull`，再启动本地镜像。保持 `CONFIG_DIR`、`USERDATA_DIR`、`MEDIA_DIR` 不变，构建或重建容器不得改变容器内 `/data/config`、`/data/userdata`、`/downloads` 的职责。

模板合并不会覆盖既有 `docker/.env`。源码构建部署如果仍设置 `BUILD_LOCAL=false`，必须手动改成 `true`，否则 `git pull` 后不会运行新源码，而会拉取配置的仓库镜像或继续使用已导入镜像，具体取决于 `PULL_IMAGE`。

## 5. 私有离线镜像与冻结镜像后备

镜像构建、隔离验证、`docker save/load`、校验和与 Container Station 导入边界以[Docker 镜像打包与离线交付](Docker镜像打包与离线交付.md)为准。自有设备导入当前源码构建的私有离线包后，可以设置：

```env
BILI_IMAGE=<已导入的镜像名与标签>
BUILD_LOCAL=false
PULL_IMAGE=false
```

启动脚本会确认镜像已存在，并使用 `--no-build` 启动，不拉取仓库镜像，也不把设备上的旧源码重新构建成同名镜像。私有离线交付不恢复 tag、GitHub Release 或 GHCR 正式发布能力。

确实无法在设备上构建时，可以显式使用既有历史镜像：

```env
BILI_IMAGE=ghcr.io/kachekakaka/bili_workspace:v0.7.0
BUILD_LOCAL=false
PULL_IMAGE=true
```

该镜像只对应 V0.7.0，不接收后续源码更新；不要使用它判断当前 `main` 的行为。恢复到本地构建时重新设置 `BUILD_LOCAL=true`。

## 6. 数据库迁移

所有数据库迁移必须满足一致性备份、单事务、失败回滚、外键检查、未来 schema 拒绝降级和最近 3 份备份。

当前数据库 schema 为 v4。旧库升级到 v4 时，迁移前备份位于 `userdata/backups/`；V0.7.0 本身不增加新的数据库迁移。

## 7. 代码回滚

回滚前停止应用并备份现场。优先使用已验证 commit；既有历史 tag 也可以用于恢复相应历史版本：

```bash
git fetch origin
git checkout <已验证提交或既有历史标签>
```

然后保持持久化目录不变，执行对应版本验证并重新启动。V0.7.0 与 v0.6.2 都使用 schema v4，二者之间正常回滚无需数据库降级；跨 schema 回滚必须同时恢复匹配的迁移前备份。

不得在未备份情况下覆盖故障现场，也不得在应用运行时替换 SQLite 主文件。

## 8. 数据恢复

安全顺序：

1. 停止应用或容器；
2. 保存当前故障现场；
3. 恢复同一时间点的数据库、WAL/SHM、索引和媒体；
4. 切换匹配的代码提交；
5. 启动并核对用户、会话、任务、导出、作品、标签、删除历史和播放记录。

只恢复数据库或只恢复媒体都可能造成状态不一致。

## 9. 自主管理的恢复资产

GitHub 不应是唯一备份位置。用户应在自己的 NAS 或受控存储中保留：

```text
完整 Git Bundle
Windows 完整恢复包
Docker 镜像打包说明、离线包及其校验和
依赖与运行资产校验文件
重要变更的验证记录
```

这些恢复资产由用户自行保存，不构成项目正式发布。
