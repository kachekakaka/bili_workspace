# 源码更新、验证与回滚流程

## 1. 停止正式发布后的边界

源码以普通 Git 文件直接存在于 `main`，禁止通过压缩分片、Base64 或运行时恢复源码。项目停止未来正式发布：源码 push、PR、合并和普通 CI 都不得创建新版本 tag、GitHub Release，也不得推送或更新 GHCR 正式镜像。

活动自动化只允许：

- 检查源码结构、编译、静态规则、测试和前端语法；
- 构建但不推送 Docker amd64/arm64 镜像；
- 在具体测试协议允许时上传有保留期限的短期诊断产物；Windows 候选 EXE 不上传。

既有 `v0.7.0` tag、GitHub Release 和 GHCR 镜像保留为冻结历史状态，不代表后续 `main`。恢复任何正式发布能力都必须先形成新的显式决策，并分别取得修改与发布授权。

## 2. 源码验证

完整源码验证只从测试治理入口选择，不在运维手册复制第二套命令：

- [T-DOC 文档机械门禁](../../SoftwareTesting/doc_consistency/README.md)独立检查活动文档、归档索引和骨架入口；
- [T-PROJECT 项目完整自检](../../SoftwareTesting/project/README.md)统一执行源码、Python、Node 和 Playwright 阶段；
- [T-DOCKER Docker 镜像构建验证](../../SoftwareTesting/docker/README.md)在镜像输入受影响时承接当前项目镜像的实际构建与不发布断言；
- [T-LAUNCHER Windows 启动器测试](../../SoftwareTesting/launcher/README.md)承接 EXE、内置资源、数据根和网络安全验证。

普通验证是默认层级；全量测试和正式认证只在用户明确选择后执行。具体执行授权与高风险边界以[项目协作约束](../../AGENTS.md#授权与安全)为准。

T-PROJECT full 必须实际执行 Playwright 阶段；缺少前置时为 `blocked`。T-PROJECT 不自动下载安装浏览器。

## 3. Windows 源码、候选与打包快照

`git pull` 只更新源码，不会自动重建仓库中的 Windows 打包快照。查看或运行跟踪快照前先核对配套构建记录：

```powershell
git pull --ff-only origin main
.\dist\bili-workspace-launcher-0.7.0.exe
```

上述 EXE 是手工晋升的打包快照，可能落后于刚拉取的 `main`；只有它支持目标数据库 schema 时才能启动。内嵌输入变化后的日常验证使用 `scripts/windows/validate-launcher-candidate.bat`，候选默认在通过后精确清理，不替换快照或上传。只有维护者明确决定晋升、源码已提交且工作树干净时，才运行 `scripts/windows/build-launcher.bat` 成对更新 `dist` 与 `launcher/current-build.json`；脚本不会 commit、push 或发布。

EXE 同级 `launcher.json` 只保存最近数据根等可重建控制状态；网络安全设置、配置、数据库和媒体都在用户选择的数据根。更新 EXE 不会覆盖这些数据。需要源码、镜像或启动器验证时，从测试治理入口选择 T-PROJECT、T-DOC、T-DOCKER 或 T-LAUNCHER，不恢复旧 `verify.bat` 链。

## 4. Docker 源码构建与更新

新部署的 `docker/.env.default` 使用：

```env
BILI_IMAGE=bili-workspace:local
BUILD_LOCAL=true
PULL_IMAGE=true
```

更新：

```bash
git pull --ff-only origin main
./docker/build-and-start.sh
```

脚本从当前检出源码执行 `docker compose build --pull`，再启动本地镜像。保持 `CONFIG_DIR`、`USERDATA_DIR`、`MEDIA_DIR` 不变，构建或重建容器不得改变容器内 `/data/config`、`/data/userdata`、`/downloads` 的职责。

模板合并不会覆盖既有 `docker/.env`。源码构建部署如果仍设置 `BUILD_LOCAL=false`，必须手动改成 `true`，否则 `git pull` 后不会运行新源码，而会拉取配置的仓库镜像或继续使用已导入镜像，具体取决于 `PULL_IMAGE`。

## 5. 私有离线镜像与冻结镜像后备

镜像构建、隔离验证、`docker save/load`、校验和与 Container Station 导入边界以[Docker 镜像打包与离线交付](Docker镜像打包与离线交付.md)为准。自有设备导入当前源码构建的私有离线包后，可以设置：

```env
BILI_IMAGE=<已导入的镜像名与标签>
BUILD_LOCAL=false
PULL_IMAGE=false
```

启动脚本会确认镜像已存在，并使用 `--no-build` 启动，不拉取仓库镜像，也不把设备上的旧源码重新构建成同名镜像。私有离线交付不恢复 tag、GitHub Release 或 GHCR 正式发布能力。

确实无法在设备上构建时，可以显式使用既有历史镜像：

```env
BILI_IMAGE=ghcr.io/kachekakaka/bili_workspace:v0.7.0
BUILD_LOCAL=false
PULL_IMAGE=true
```

该镜像只对应 V0.7.0，不接收后续源码更新；不要使用它判断当前 `main` 的行为。恢复到本地构建时重新设置 `BUILD_LOCAL=true`。

## 6. 数据库迁移

所有数据库迁移必须满足一致性备份、单事务、失败回滚、外键检查、未来 schema 拒绝降级和最近 3 份备份。

当前 `main` 的数据库 schema 为 v5。旧库升级到 v4 或 v5 时，迁移前备份位于所选数据根的 `userdata/backups/`；冻结的 V0.7.0 发布物仍停留在 schema v4。

## 7. 代码回滚

回滚前停止应用并备份现场。优先使用已验证 commit；既有历史 tag 也可以用于恢复相应历史版本：

```bash
git fetch origin
git checkout <已验证提交或既有历史标签>
```

然后保持持久化目录不变，执行对应版本验证并重新启动。当前 `main` 使用 schema v5，冻结的 V0.7.0 与 v0.6.2 发布物使用 schema v4；从当前源码回滚到这些发布物属于跨 schema 回滚，必须同时恢复匹配的 v4 迁移前备份，不能只替换代码或 EXE。

不得在未备份情况下覆盖故障现场，也不得在应用运行时替换 SQLite 主文件。

## 8. 数据恢复

安全顺序：

1. 停止应用或容器；
2. 保存当前故障现场；
3. 恢复同一时间点的数据库、WAL/SHM、索引和媒体；
4. 切换匹配的代码提交；
5. 启动并核对用户、会话、任务、导出、作品、标签、删除历史和播放记录。

只恢复数据库或只恢复媒体都可能造成状态不一致。

## 9. 自主管理的恢复资产

GitHub 不应是唯一备份位置。用户应在自己的 NAS 或受控存储中保留：

```text
完整 Git Bundle
Windows 打包快照 EXE、`launcher/current-build.json` 与校验记录
Docker 镜像打包说明、离线包及其校验和
依赖与内置资源校验文件
重要变更的验证记录
```

这些恢复资产由用户自行保存，不构成项目正式发布。
