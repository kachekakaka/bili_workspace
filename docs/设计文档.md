## 1. 运行时与目录职责

- `app/` 是 Python 后端，负责 HTTP API、认证、任务队列、搜索适配、媒体索引、SQLite 持久化和运行时状态。
- `web/` 是无构建步骤的浏览器前端；服务端直接提供静态资源。
- `launcher/` 是 Windows amd64 单文件启动器，负责数据根选择、资源展开、后端生命周期、网络安全设置和固定 Docker 导出。
- `app/defaults/` 保存 Windows 启动器与 Docker 共用的只读模板；实际值不进入 Git。
- Windows 仓库入口为手工晋升的打包快照 `dist/bili-workspace-launcher-0.7.0.exe`，可能落后于 `main`；Docker 入口为 `docker/build-and-start.sh` 与 `docker/compose.yaml`。

Windows 由用户选择仓库外数据根，其中 `config/`、`userdata/`、`downloads/` 分别承接配置与凭据、SQLite 与运行状态、永久媒体；`launcher.json`、已校验资源和任务工作区只位于 EXE 同级控制根。Docker 把宿主机的 `CONFIG_DIR`、`USERDATA_DIR`、`MEDIA_DIR` 分别映射到 `/data/config`、`/data/userdata`、`/downloads`。非 Docker、非启动器进程没有仓库内生产数据回退。

HTTP API 由 `app/main.py` 作为唯一组合根，显式注册账号、系统、任务和作品库四个领域 Router。账号、系统与作品库 Router 位于 `app/routes.py`，任务 Router 位于 `app/task_routes.py`；组合后的每个 HTTP 方法与路径只有一个权威处理器，注册顺序不承担覆盖或版本选择职责。认证、统一响应和任务呈现辅助逻辑只有一份现行实现。

## 2. 前端架构与页面生命周期

- `web/index.html` 只加载第三方 `qrcode.min.js` 和唯一应用入口 `web/assets/app/main.mjs`。
- 前端使用浏览器原生 `.mjs` ES Modules 和静态 import，不依赖 npm、打包器或生产 Node 运行时。
- 页面模块位于 `web/assets/app/pages/`，每个路由只有一个正式 renderer。页面统一导出 `mount(root, context)`，并返回可重复调用的 `dispose()`。
- Router 在每次切页时递增 generation、终止上一页 `AbortController`、调用上一页 `dispose()`；只有当前 generation 可以提交结果。
- API client、Session store、Context store、Modal、Toast、Confirm 和 TaskStream 各只有一份实现。
- `ResourceCache` 在当前认证会话内按稳定参数键保存最近成功结果、合并同键并发请求并发布 stale 状态。底层请求由缓存自有 `AbortController` 管理；路由中止只取消该页面消费者，显式失效或登出才终止共享请求并清空数据。
- Dashboard 与 Tasks 通过租约使用同一个 TaskStream：Dashboard 请求 `summary`，Tasks 请求 `full`，完整租约优先；任一时刻最多一个 `/api/events` EventSource。模式切换会隔离并重置两种快照，零租约、会话失效或登出时关闭连接。
- 跨页面交接使用一次性路由状态，不使用遗留全局业务对象。
- CSS 位于 `web/assets/styles/`，按 tokens、base、components、pages 四层组织。
- 当前结构不包含旧 `app.js`、`enhancements-*` renderer/overlay、Legacy Bridge、页面 MutationObserver、捕获阶段事件抢占或版本专用 CSS 覆盖。
- 浏览器资源版本与服务版本不一致时，App Shell 提供重启服务和强制刷新提示；`.mjs` 参与源码构建指纹。

## 3. 搜索调用链与缓存

管理员视频关键词继续进入 `/api/search`；UP 主名称候选、精确定位和投稿页分别进入 `/api/bilibili/creators/search`、`/api/bilibili/creators/resolve` 与 `/api/bilibili/creators/{uid}/submissions`。普通用户中间件只精确放行后两个读取入口，名称搜索和管理员搜索仍拒绝。服务端通过同一 WBI/Cookie 适配边界请求一个原始页，再按当前认证拥有者和下载目标装饰本地状态；标题的精准/模糊筛选只在浏览器当前页执行。

- WBI 密钥按 Bilibili Cookie 指纹缓存，缓存时长以[字段契约](字段契约.md)为准；签名失效时清除缓存并最多重试一次。
- 原始页按字段契约规定的时长缓存，键包含读取模式、规范关键词或 UID、Bilibili 排序、页码和 Cookie 指纹，不包含网站用户、本地状态、标签或浏览器标题筛选。
- 浏览器按发现上下文、排序、页码和下载目标维护当前网站会话内的 24 页 LRU；读取命中会提升最近使用顺序，身份改变时清空，避免无界增长或跨账号复用。
- `submissionScanDecision` 驱动关键词和投稿的按需顺序续页：当前页没有可下载候选才请求下一页，找到即停，每轮最多 10 页；停止、同页重试和从下一批继续都由显式状态承载，不执行推测性预取。
- `AbortController` 和 Router generation 共同阻止旧响应写入新页面。
- “刷新 B站结果”使当前原始页缓存失效；普通标题筛选不触碰服务端缓存。
- `app/search.py` 在返回搜索、UP 主资料或投稿前将协议相对图片及 HTTP 图片统一规范为 HTTPS；`app/routes.py` 随后只保留受信 Bilibili 图片域名，前端仍通过封面代理和加载失败占位图收口。

概览作品卡把媒体 ID 写入独立的一次性 `sessionStorage` 键后导航到作品库。作品库挂载时读取并立即删除该键，完成当前页加载后直接调用既有按媒体 ID 的详情接口，因此不会改变路由参数，也不依赖当前分页命中。

## 4. 下载、画质与任务队列

`DownloadRequest` 先经过严格字段校验和权限收敛，再由当前认证会话注入拥有者。管理员可以创建媒体库或设备导出任务；普通用户的目标、分组、强制标志、最低清晰度和目标档位由服务端覆盖为设备导出、全局门槛和自动最高等安全值。

下载前由适配层取得码流信息并执行最低清晰度或指定档位预检；任务完成后再次检查实际媒体流。底层下载器封装在适配层中，API、任务模型和质量判定不依赖单一工具的私有输出格式。

`TaskQueue` 是两条下载队列共同使用的唯一生命周期实现，任务对象直接持有拥有者、公开源标识和必要的内部命名空间键；不存在所有权子类或运行时方法替换。正式任务写入 SQLite `task_records`，运行队列保存可恢复的活动状态：

1. 创建请求规范化源键并检查批量上限、用户活动任务上限和重复活动任务；
2. 队列创建任务，写入 `owner_user_id`、`destination`、源键及显示元数据；
3. worker 在受限并发下执行下载、混流、画质复核和索引更新；
4. 快照更新 SQLite，日志写入用户数据目录并限制尾部与文件大小；
5. 终态触发按用户的历史清理；异常重启后的运行中任务只能标记中断或重新排队，不能误判成功。

直接输入继续使用 `/api/download` 的兼容“重复则跳过”合同；搜索与投稿选择使用 `/api/download/selection` 的严格合同。严格路径在对应队列锁内完成整批重复、索引、容量和拥有者配额判断，随后以一个 SQLite 事务写入全部 `task_records` 与设备 `exports`，事务成功后才整体发布到内存队列并唤醒 worker。发布异常在锁释放前移除整批内存状态并精确补偿数据库，因此失败响应不会留下部分可见任务。

`CreatorImportManager` 由 `AppState` 持有，使用一个协调线程和 FIFO 等待序列保存最近 20 个当前运行期作业。开始请求只接收 UID、分组 ID 和最低清晰度，拥有者取管理员会话，目标固定为媒体库；相同 UID 的活动或等待作业幂等复用。应用关闭时先停止该管理器，再停止下载队列和数据库。

发现阶段固定调用 `creator_submissions(order="pubdate")`，记录发起时间截止点，按 BV 去重并过滤截止点之后的投稿。遍历期间总数或页数变化时从第一页做最多三轮稳定性复核；分页有限重试仍失败时保留原页和已经发现的项供本次进程继续。稳定遍历后按发布时间倒序处理，每项在入队前重新查询活动任务、有效媒体索引和删除历史。

全量入库不调用 100 项手工批量入口，而对每个未分类投稿执行一次严格单项入队，并沿用 `TaskStore.register_task_batch` 的发布前持久化和失败补偿。管理器创建的活动任务不超过下载并发数，同时从 `MAX_PENDING_TASKS` 尾部保留同等数量（队列上限为 1 时除外）供手工提交；容量不足只等待。单项失败隔离为作业失败项，取消信号只阻止后续发现和创建，不撤销已经发布的任务。

管理员 API 提供开始、列表、详情、取消、失败页继续和失败项重试。`submission-browser.mjs` 只在管理员媒体库目标下显示当前 UID 入口和状态，`tasks-impl.mjs` 显示全局运行期作业；两者仅在页面挂载期间轮询作业，不改变现有任务 SSE。

所有终态重试都复用原任务 ID、原拥有者和最初创建时间，并清空上次执行状态、结果与日志，只保留最新一次执行。暂停/继续复用任务记录，但只有底层工具明确提供且经过验证时才能声称字节级续传。

队列停止意图与终态提交分离：运行中暂停/取消先保持 `status=running` 并写入 `phase=pausing/cancelling`，实际执行停止后才由 `_finish` 一次性提交 `status=cancelled` 与 `phase=paused/cancelled`。暂停可以被取消升级，取消不能被暂停降级；重复同意图按幂等结果返回。阶段或进度只有在公开字段真实变化时才通知，持久化回调完成后才递增变更计数，确保 SSE 不会先看到计数、后看到旧数据库快照。

`run_bbdown_info` 与正式下载共用可取消的流式子进程和进程树终止策略，但信息探测仍使用独立的 `MAX_INFO_OUTPUT_CHARS` 容量。同步元数据读取无法被线程外强杀；其等待期间保留 stopping 阶段，返回后先检查取消事件，不再启动信息探测或正式下载。

## 5. 认证、会话与权限

- 密码使用 scrypt 哈希；会话明文 Token 只存在于 HttpOnly Cookie，SQLite 只保存 SHA-256 哈希。
- HTTP Cookie 名为 `bili_session`；HTTPS 使用带 Secure 的 `__Host-bili_session`。两者均使用 `SameSite=Lax; Path=/`。
- 每个会话拥有独立 CSRF Token；写请求通过 `X-CSRF-Token` 校验当前会话，其他会话的 Token 无效。
- 会话绝对有效期、`last_seen_at` 最短更新间隔和单用户有效会话上限以[字段契约](字段契约.md)为准；超过上限时，在同一事务中按 `last_seen_at`、`created_at`、`id` 撤销最久未连接会话。
- 修改密码在一个事务边界内更新密码哈希、清除强制改密、轮换当前 Token/CSRF，并撤销其他会话。
- 认证中间件在强制改密状态下只允许认证状态、改密和退出路径。
- 权限由后端角色矩阵执行；前端导航过滤只用于呈现。普通用户访问他人对象时返回与不存在相同的结果，避免对象枚举。
- 审计日志只记录会话和目标用户标识等必要元数据，不记录密码、明文 Token、完整 Cookie 或未脱敏任务日志。

## 6. 任务所有权、保留与设备导出

`owner_user_id` 只能取自服务端认证上下文，客户端同名字段、`user_id`、角色或权限字段不参与归属。管理员重试普通用户任务时保留原拥有者。

任务查询以 SQLite 为权威：普通用户固定按本人拥有者过滤；管理员可以组合拥有者、状态、目标、关键词、时间排序字段和方向。前端不先读取全部任务再本地全量排序。

终态清理按用户及[字段契约](字段契约.md)规定的保留期限和数量上限执行。清理同步移除任务记录、兼容快照、任务日志、失效导出元数据和对应普通下载审计记录，但临时文件仍由设备导出生命周期处理。

设备导出以 `owner_user_id + source_key` 判断同一用户的有效任务。队列内部使用拥有者哈希命名空间隔离同作品任务，API 继续显示原始 source key。服务端只接受数据库导出对象 ID，不接受任意路径。

导出文件完整发送后，`TaskStore` 在一个事务内首次写入 `exports.downloaded_at`、把清理目标设为 `downloaded`，并只为普通用户 upsert `device_download_history`；随后才清理文件。连接中断、HEAD 和未消费完整响应不调用该完成边界。清理失败保留 `cleanup_pending + cleanup_target_state`，后台只重试文件清理并进入原目标状态，不制造新的领取时间。准备中、已就绪或等待清理的导出不作为普通终态历史删除；设备下载事实独立于任务与导出历史保留。

## 7. SQLite、迁移与恢复

当前数据库 schema 为 v5，核心表包括用户、会话、审计、任务记录、设备导出、设备下载记录、媒体索引、标签关系、删除历史和观看状态。`AppState` 只构造一个具体 `Database`，由它唯一拥有 SQLite 连接、PRAGMA、完整 schema、迁移、备份、显式事务和关闭；`AuthStore`、`TaskStore`、`CatalogStore`、`TagStore` 与 `DeletionStore` 通过组合共享该数据库，不自建连接或 schema。`LibraryService` 只编排跨索引、文件和多个领域 Store 的作品库用例，不增加通用 Repository 或可替换数据库接口。外键始终开启。

升级旧数据库时：

1. 先使用 SQLite `backup()` 在 `userdata/backups/` 创建一致性备份；
2. 按[字段契约](字段契约.md)规定的上限，只保留最近的备份；
3. 在 `BEGIN IMMEDIATE` 单事务中执行结构和数据迁移；
4. 提交前执行 `PRAGMA foreign_key_check`；
5. 任一步失败就回滚且不开放 HTTP 服务；未来 schema 数据库拒绝被旧代码静默降级。

升级到 v4 时，旧任务快照和设备导出归属原管理员；v3→v4 不重复撤销此前已经建立的有效会话。v4→v5 新增设备下载记录和导出清理目标，只从普通用户、非空作品键、明确 `downloaded` 且已有领取时间的记录回填；旧 `cleanup_pending` 无法证明领取来源，保守映射为非领取清理目标。回滚跨 schema 版本时必须停止应用、恢复匹配的迁移前数据库备份并切换匹配代码；运行中不得覆盖 SQLite 主文件。

## 8. 配置合并与秘密边界

Git 只跟踪 `app/defaults/` 下三份应用模板和 `docker/.env.default`。实际配置不存在时从模板创建；存在时按以下规则合并：

- JSON 递归补入模板新增而实际缺少的字段；dotenv 只追加缺失键；
- 保留已有值、额外字段、空字符串、`0`、`false` 和用户选择；
- 使用原子写入并保留备份，拒绝符号链接配置目标；
- 损坏配置不能用模板静默覆盖。

Bilibili 凭据在 Windows 保存于 `<data-root>/config/bbdown/BBDown.data`，Docker/NAS 保存于 `/data/config/bbdown/BBDown.data`。完整 Cookie 不返回浏览器、不写日志、不进入 Git 或验证产物。

## 9. 媒体、Range 与兼容副本

媒体响应支持 `HEAD` 和单范围字节读取，正确返回 `206`、`416` 与 `ETag`，并在客户端断开后停止继续读取。原始媒体是权威文件；H.264/AAC MP4 兼容副本是按需派生物，不能覆盖原文件。

作品库筛选、分页和排序由数据库执行。分组显示名与稳定目录键分离；普通重命名只更新元数据。标签关系和 `deleted_media` 独立保存，删除历史不借用标签模型。

作品删除由 `LibraryService` 以单个作品为提交单位协调。保留文件时只移除索引与逻辑记录；要求删除文件时先完成所选文件操作，再在一个 SQLite 事务中删除媒体记录、标签并写入删除历史。文件步骤或数据库提交失败都不报告成功，并按实际文件恢复可重试的索引和媒体文件记录；已实际删除的文件不伪装成可回滚。批量入口去重后逐项执行并分别返回成功与错误。

## 10. 网络与容器安全

- 监听地址和端口来自配置，不写死在应用代码中；可信 Host 与可信代理来源分别校验。
- 公网 Cookie、HTTPS 与 HSTS 由显式配置启用；HSTS 不在尚未验证 HTTPS 时自动开启。
- Docker 容器以配置的 PUID/PGID 非 root 运行，根文件系统只读，丢弃 capabilities，不使用 privileged，不挂载 Docker socket。
- `/tmp` 使用受限 tmpfs；持久化写入只发生在三个显式映射目录。
- 容器具有健康检查、日志大小/数量限制和 45 秒优雅停止窗口。

## 11. 性能与资源边界

- 下载并发、转码线程、导出 TTL 和最低剩余空间均由配置限制。
- 开始下载或转码前检查临时盘和媒体盘剩余空间。
- 作品库使用服务端分页；封面懒加载并受控缓存。
- 任务日志、API 日志尾部、信息探测输出、封面缓存、兼容副本和导出临时文件均有大小、数量或 TTL 边界。
- 请求体、单次批量项数、输入长度和排队任务数设有硬上限，避免单个请求无界占用内存或队列。
- 全量入库最多保留 20 个运行期终态，源分页最多接受 10000 页并使用可取消的有界重试；其协调线程、容量等待和页面轮询都随应用或页面生命周期停止。
- `IndexStore.snapshot_if_changed(previous_token)` 在同一锁内刷新外部变化、比较 token，并且只在 token 变化时深拷贝索引；`CatalogStore.sync_index` 只确认本轮实际处理的 token，使同步期间的新变更留到下一轮处理。
- `/api/events?view=summary` 直接用 SQLite `GROUP BY status` 生成任务计数，只发送 `summary + at`；默认 `full` 模式发送 `tasks + summary + at`。两种浏览器快照不互相继承完整任务数据。
- Dashboard、Library 和 Groups 采用缓存首屏加后台刷新；Account 先显示最近状态再强制验证 Bilibili 登录；Settings 复用共享状态但始终新取配置。Library 查询缓存按完整筛选参数隔离，单项选择与标签更新使用局部 DOM/缓存修补，写操作显式使摘要、最近作品和其他查询页失效。

## 12. 源码验证、Windows 候选与停止发布

- `.github/workflows/ci.yml` 只执行验证并在失败诊断需要时上传有期限的隔离 run；启动器 workflow 构建临时候选但不上传候选 EXE，也不写回仓库。
- `tools.build_launcher` 是候选与正式快照的唯一构建实现。两个模式都验证固定资源、工具、PE amd64、文件名、大小、EXE 自检，并让候选 EXE 在仓库外全新临时数据根启动当前后端，核对健康身份、数据库 schema 与根页面后只停止自有进程。
- `scripts/windows/validate-launcher-candidate.bat` 创建带所有权标记的唯一忽略目录，候选成功后默认精确清理，只接受显式保留开关；它不能写 `dist` 或规范构建记录。`scripts/windows/build-launcher.bat` 是独立的人工快照入口，只接受干净、已提交的 `HEAD`，在发布前再次核对身份并成对更新 EXE 与构建记录。
- schema 2 构建记录以 `artifact_kind` 区分候选和快照，记录完整 `source_commit`、`source_dirty` 及两类 EXE 检查。`build_id` 继续覆盖实际内嵌输入；当前仓库中的正式快照已使用 schema 2，精确身份以 `launcher/current-build.json` 为准。
- `.github/workflows/docker-image.yml` 只验证 amd64/arm64 Docker 构建：权限为 `contents: read`，不登录 GHCR，不具备 `packages: write`，并使用 `push: false`。
- 活动 workflows 中不存在创建 tag、GitHub Release、发布 GHCR 镜像或更新 `latest` 的路径；版本专用发布 workflow 只保留在归档。
- Docker 新配置默认以当前检出源码构建本地镜像。配置同步不覆盖既有 `.env`，因此旧部署必须由维护者显式把 `BUILD_LOCAL` 切换为 `true`。
- 既有 V0.7.0 tag、Release 和 GHCR 镜像是冻结历史状态，不参与后续源码交付。
- 如果未来恢复正式发布能力，必须先形成新的架构决策，并分别取得修改与发布授权。
