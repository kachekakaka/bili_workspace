## 1. 运行时与目录职责

- `app/` 是 Python 后端，负责 HTTP API、认证、任务队列、搜索适配、媒体索引、SQLite 持久化和运行时状态。
- `web/` 是无构建步骤的浏览器前端；服务端直接提供静态资源。
- `launcher/` 是 Windows amd64 单文件启动器，负责数据根选择、资源展开、后端生命周期、网络安全设置和固定 Docker 导出。
- `app/defaults/` 保存 Windows 启动器与 Docker 共用的只读模板；实际值不进入 Git。
- Windows 入口为 `dist/bili-workspace-launcher-0.7.0.exe`；Docker 入口为 `docker/build-and-start.sh` 与 `docker/compose.yaml`。

Windows 由用户选择仓库外数据根，其中 `config/`、`userdata/`、`downloads/` 分别承接配置与凭据、SQLite 与运行状态、永久媒体；`launcher.json`、已校验资源和任务工作区只位于 EXE 同级控制根。Docker 把宿主机的 `CONFIG_DIR`、`USERDATA_DIR`、`MEDIA_DIR` 分别映射到 `/data/config`、`/data/userdata`、`/downloads`。非 Docker、非启动器进程没有仓库内生产数据回退。

## 2. 前端架构与页面生命周期

- `web/index.html` 只加载第三方 `qrcode.min.js` 和唯一应用入口 `web/assets/app/main.mjs`。
- 前端使用浏览器原生 `.mjs` ES Modules 和静态 import，不依赖 npm、打包器或生产 Node 运行时。
- 页面模块位于 `web/assets/app/pages/`，每个路由只有一个正式 renderer。页面统一导出 `mount(root, context)`，并返回可重复调用的 `dispose()`。
- Router 在每次切页时递增 generation、终止上一页 `AbortController`、调用上一页 `dispose()`；只有当前 generation 可以提交结果。
- API client、Session store、Context store、Modal、Toast、Confirm 和 TaskStream 各只有一份实现。
- Dashboard 和 Tasks 订阅同一个 TaskStream；登录状态下最多存在一个 `/api/events` EventSource，登出时关闭并清空共享状态。
- 跨页面交接使用一次性路由状态，不使用遗留全局业务对象。
- CSS 位于 `web/assets/styles/`，按 tokens、base、components、pages 四层组织。
- 当前结构不包含旧 `app.js`、`enhancements-*` renderer/overlay、Legacy Bridge、页面 MutationObserver、捕获阶段事件抢占或版本专用 CSS 覆盖。
- 浏览器资源版本与服务版本不一致时，App Shell 提供重启服务和强制刷新提示；`.mjs` 参与源码构建指纹。

## 3. 搜索调用链与缓存

浏览器把 Bilibili 关键词、排序和页码提交到单一 `/api/search`。服务端通过 WBI 适配层请求 Bilibili 当前页，并把标签、下载状态和删除状态合并进同一响应；标题的精准/模糊筛选只在浏览器当前页执行。

- WBI 密钥按 Bilibili Cookie 指纹缓存，缓存时长以[字段契约](字段契约.md)为准；签名失效时清除缓存并最多重试一次。
- 原始搜索页按字段契约规定的时长缓存，缓存键只包含关键词、Bilibili 排序、页码和 Cookie 指纹，不包含浏览器标题筛选词或筛选模式。
- 当前页显示成功后，浏览器空闲任务最多预取下一页一次；查询改变、路由离开、省流量模式或当前页失败时取消预取。
- `AbortController` 和 Router generation 共同阻止旧响应写入新页面。
- “刷新 B站结果”使当前原始页缓存失效；普通标题筛选不触碰服务端缓存。

## 4. 下载、画质与任务队列

`DownloadRequest` 先经过严格字段校验和权限收敛，再由当前认证会话注入拥有者。管理员可以创建媒体库或设备导出任务；普通用户的目标、分组和强制标志由服务端覆盖为设备导出安全值。

下载前由适配层取得码流信息并执行最低清晰度或指定档位预检；任务完成后再次检查实际媒体流。底层下载器封装在适配层中，API、任务模型和质量判定不依赖单一工具的私有输出格式。

正式任务写入 SQLite `task_records`，运行队列只保存可恢复的活动状态：

1. 创建请求规范化源键并检查批量上限、用户活动任务上限和重复活动任务；
2. 队列创建任务，写入 `owner_user_id`、`destination`、源键及显示元数据；
3. worker 在受限并发下执行下载、混流、画质复核和索引更新；
4. 快照更新 SQLite，日志写入用户数据目录并限制尾部与文件大小；
5. 终态触发按用户的历史清理；异常重启后的运行中任务只能标记中断或重新排队，不能误判成功。

重试复用原任务 ID 和原拥有者。暂停/继续复用任务记录，但只有底层工具明确提供且经过验证时才能声称字节级续传。

## 5. 认证、会话与权限

- 密码使用 scrypt 哈希；会话明文 Token 只存在于 HttpOnly Cookie，SQLite 只保存 SHA-256 哈希。
- HTTP Cookie 名为 `bili_session`；HTTPS 使用带 Secure 的 `__Host-bili_session`。两者均使用 `SameSite=Lax; Path=/`。
- 每个会话拥有独立 CSRF Token；写请求通过 `X-CSRF-Token` 校验当前会话，其他会话的 Token 无效。
- 会话绝对有效期、`last_seen_at` 最短更新间隔和单用户有效会话上限以[字段契约](字段契约.md)为准；超过上限时，在同一事务中按 `last_seen_at`、`created_at`、`id` 撤销最久未连接会话。
- 修改密码在一个事务边界内更新密码哈希、清除强制改密、轮换当前 Token/CSRF，并撤销其他会话。
- 认证中间件在强制改密状态下只允许认证状态、改密和退出路径。
- 权限由后端角色矩阵执行；前端导航过滤只用于呈现。普通用户访问他人对象时返回与不存在相同的结果，避免对象枚举。
- 审计日志只记录会话和目标用户标识等必要元数据，不记录密码、明文 Token、完整 Cookie 或未脱敏任务日志。

## 6. 任务所有权、保留与设备导出

`owner_user_id` 只能取自服务端认证上下文，客户端同名字段、`user_id`、角色或权限字段不参与归属。管理员重试普通用户任务时保留原拥有者。

任务查询以 SQLite 为权威：普通用户固定按本人拥有者过滤；管理员可以组合拥有者、状态、目标、关键词、时间排序字段和方向。前端不先读取全部任务再本地全量排序。

终态清理按用户及[字段契约](字段契约.md)规定的保留期限和数量上限执行。清理同步移除任务记录、兼容快照、任务日志、失效导出元数据和对应普通下载审计记录，但临时文件仍由设备导出生命周期处理。

设备导出以 `owner_user_id + source_key` 判断同一用户的有效任务。队列内部使用拥有者哈希命名空间隔离同作品任务，API 继续显示原始 source key。服务端只接受数据库导出对象 ID，不接受任意路径。

导出文件完整发送后删除；连接中断时保留到 TTL。准备中、已就绪或等待清理的导出不作为普通终态历史删除。

## 7. SQLite、迁移与恢复

当前数据库 schema 为 v4，核心表包括用户、会话、审计、任务记录、设备导出、媒体索引、标签关系、删除历史和观看状态。外键始终开启。

升级旧数据库时：

1. 先使用 SQLite `backup()` 在 `userdata/backups/` 创建一致性备份；
2. 按[字段契约](字段契约.md)规定的上限，只保留最近的备份；
3. 在 `BEGIN IMMEDIATE` 单事务中执行结构和数据迁移；
4. 提交前执行 `PRAGMA foreign_key_check`；
5. 任一步失败就回滚且不开放 HTTP 服务；未来 schema 数据库拒绝被旧代码静默降级。

升级到 v4 时，旧任务快照和设备导出归属原管理员。v3→v4 迁移不重复撤销此前已经建立的有效会话。回滚跨 schema 版本时必须停止应用、恢复匹配的迁移前数据库备份并切换匹配代码；运行中不得覆盖 SQLite 主文件。

## 8. 配置合并与秘密边界

Git 只跟踪 `app/defaults/` 下三份应用模板和 `docker/.env.default`。实际配置不存在时从模板创建；存在时按以下规则合并：

- JSON 递归补入模板新增而实际缺少的字段；dotenv 只追加缺失键；
- 保留已有值、额外字段、空字符串、`0`、`false` 和用户选择；
- 使用原子写入并保留备份，拒绝符号链接配置目标；
- 损坏配置不能用模板静默覆盖。

Bilibili 凭据在 Windows 保存于 `<data-root>/config/bbdown/BBDown.data`，Docker/NAS 保存于 `/data/config/bbdown/BBDown.data`。完整 Cookie 不返回浏览器、不写日志、不进入 Git 或验证产物。

## 9. 媒体、Range 与兼容副本

媒体响应支持 `HEAD` 和单范围字节读取，正确返回 `206`、`416` 与 `ETag`，并在客户端断开后停止继续读取。原始媒体是权威文件；H.264/AAC MP4 兼容副本是按需派生物，不能覆盖原文件。

作品库筛选、分页和排序由数据库执行。分组显示名与稳定目录键分离；普通重命名只更新元数据。标签关系和 `deleted_media` 独立保存，删除历史不借用标签模型。

## 10. 网络与容器安全

- 监听地址和端口来自配置，不写死在应用代码中；可信 Host 与可信代理来源分别校验。
- 公网 Cookie、HTTPS 与 HSTS 由显式配置启用；HSTS 不在尚未验证 HTTPS 时自动开启。
- Docker 容器以配置的 PUID/PGID 非 root 运行，根文件系统只读，丢弃 capabilities，不使用 privileged，不挂载 Docker socket。
- `/tmp` 使用受限 tmpfs；持久化写入只发生在三个显式映射目录。
- 容器具有健康检查、日志大小/数量限制和 45 秒优雅停止窗口。

## 11. 性能与资源边界

- 下载并发、转码线程、导出 TTL 和最低剩余空间均由配置限制。
- 开始下载或转码前检查临时盘和媒体盘剩余空间。
- 作品库使用服务端分页；封面懒加载并受控缓存。
- 任务日志、API 日志尾部、信息探测输出、封面缓存、兼容副本和导出临时文件均有大小、数量或 TTL 边界。
- 请求体、单次批量项数、输入长度和排队任务数设有硬上限，避免单个请求无界占用内存或队列。

## 12. 源码验证与停止发布

- `.github/workflows/ci.yml` 与启动器 workflow 只执行验证或上传短期验证产物，不写回仓库。
- `.github/workflows/docker-image.yml` 只验证 amd64/arm64 Docker 构建：权限为 `contents: read`，不登录 GHCR，不具备 `packages: write`，并使用 `push: false`。
- 活动 workflows 中不存在创建 tag、GitHub Release、发布 GHCR 镜像或更新 `latest` 的路径；版本专用发布 workflow 只保留在归档。
- Docker 新配置默认以当前检出源码构建本地镜像。配置同步不覆盖既有 `.env`，因此旧部署必须由维护者显式把 `BUILD_LOCAL` 切换为 `true`。
- 既有 V0.7.0 tag、Release 和 GHCR 镜像是冻结历史状态，不参与后续源码交付。
- 如果未来恢复正式发布能力，必须先形成新的架构决策，并分别取得修改与发布授权。
