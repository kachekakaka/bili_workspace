## 1. 背景与目标

当前 `T-PROJECT` 使用虚构凭据、模拟 Bilibili 响应和隔离浏览器，只能证明已建模行为；Windows 候选运行冒烟只验证健康、构建身份、数据库 schema 和根页面。它们不能发现真实登录、WBI 签名、上游响应形状、真实封面加载或 BBDown 成功链已经变化。

本方案新增独立的 `T-BILIBILI-LIVE`。仓库本地授权绑定凭据源和测试根；运行器在绑定数据根只读取身份标记、固定场景和一份 `BBDown.data`，把凭据复制到测试独占的新数据根，再按影响域验证真实成功链。真实链先于相关模拟测试运行；真实环境证明外部集成，模拟测试继续证明失败、权限、并发、队列和恢复边界。

目标如下：

1. 让维护者或 AI 能从一个稳定 Windows 脚本运行当前源码的真实发现、封面、下载、入库和页面冒烟。
2. 普通源码变化复用既有已校验启动器中的固定 BBDown/FFmpeg，不要求每次改动都重新打包；启动器或冻结资源受影响时才增加临时候选 EXE 验证。
3. 让真实公开响应自动形成完整结构候选，检测未被手工 fixture 建模的字段变化，同时不把真实身份、内容、凭据或原始现场写入仓库。
4. 以明确状态、资源上限、产物边界和人工清理规则，使真实测试可重复、可停止、可审查。

## 2. 范围与排除项

### 2.1 纳入范围

- 新增 Registry 项 `T-BILIBILI-LIVE`，执行类别为 `affected_only`，首期只支持 Windows 本地运行。
- 增加仓库本地授权与固定场景解析、隔离运行编排、真实响应记录与清洗、源码目标、候选 EXE 目标、真实浏览器步骤和结构化结果。
- 修订项目级授权约束与测试安全文档，为本套件建立唯一的真实数据窄例外；`T-PROJECT`、Playwright CI 和普通 pytest 继续禁止真实凭据与真实 Bilibili。
- 提供只读的过期运行列举和精确单目录清理能力；删除动作只在维护者明确指定后执行。

### 2.2 不纳入范围

- 不扫描磁盘、`launcher.json`、注册表或任意数据目录寻找登录；不把普通 `.bili-workspace-data-root.json` 当成真实测试授权。
- 不让运行器创建或修改 `.bili-workspace-live-test.json`，不在执行期读取凭据源数据库、配置、媒体或其余业务文件。
- 不把测试根放进源码仓库、凭据源、二者子目录或 `%LOCALAPPDATA%`，不建立第二套测试根环境变量。
- 不在 CI、Linux 或 macOS 运行，不安装浏览器、Python 包、BBDown 或 FFmpeg，不自动下载第三方工具。
- 不真实启动“UP 主全量入库”作业；真实链抽测严格批量下载，全部投稿的调度、去重、容量等待、取消和恢复继续由模拟测试证明。
- 不自动替换失效 BV，不自动刷新仓库 fixture，不自动删除三天外目录，不建立后台服务或 Windows 计划任务。
- 不生成或覆盖正式 EXE、规范构建记录或发布产物；临时候选只写任务目录内的 candidate 记录。不改变停止发布的现行决策，不推定 commit、push 或 PR 授权。

## 3. 授权与文件合同

### 3.1 仓库本地授权与固定场景

维护者明确要求创建后，当前仓库 Git common directory 的 `bili-workspace/automatic-live-test.json` 形成仓库本地长期授权：

```json
{
  "schema_version": 1,
  "authorization": "automatic_live_test",
  "project_id": "bili_workspace",
  "credential_source": "D:/Projects/python/bili_datas",
  "test_root": "D:/Projects/python/bili_live_runs"
}
```

该文件不在工作树内，同一仓库 worktree 共享，clone、commit 和 push 不携带。运行器只读解析并核对当前 Git common directory、日常数据根标记、固定凭据文件以及两个绝对路径边界；未知字段、身份或路径漂移均安全阻断。删除该文件即撤销当前仓库的持续真测授权。

凭据源根目录另含只提供固定目标的 `.bili-workspace-live-test.json`：

```json
{
  "schema_version": 1,
  "kind": "bili-workspace-live-test",
  "creator_uid": "10001",
  "download_bvids": [
    "BV1TEST00001",
    "BV1TEST00002",
    "BV1TEST00003",
    "BV1TEST00004",
    "BV1TEST00005",
    "BV1TEST00006",
    "BV1TEST00007",
    "BV1TEST00008"
  ]
}
```

- 固定场景必须是 UTF-8 普通文件，拒绝重解析点、未知字段、重复 BV、非正整数 UID、非法 BV 格式、非 8 项列表和超限文件。
- 创建场景文件是独立维护动作，只在维护者明确要求时执行。现有媒体索引没有 creator UID，因此获授权的维护者或 AI 先从既有记录读取必要的 BV 与时长，再通过这些作品的公开详情解析 `owner.mid` 并按 UID 分组，从同一 UID 选择 8 个较短作品；最终场景只保存 UID 和 BV，不保存原库路径、标题、作者名或详情正文。运行器只消费场景，不具备生成场景或读取来源记录的能力。
- 仓库本地授权覆盖读取其绑定数据根中的场景文件和 `config/bbdown/BBDown.data`、复制凭据到新隔离运行、按本方案访问真实 Bilibili 和产生受限下载；场景文件单独存在不授权其他 clone 或仓库使用真实环境。
- 自动命令省略 `--data-root` 和 `BILI_TEST_ROOT` 时从仓库本地授权取得二者；显式命令仍可逐次提供。仓库授权、场景或凭据任一缺失时结果为 `blocked`。
- 场景本身不含 Cookie，但仍不得进入 Git；`.gitignore` 和源码安全检查增加精确防线。

普通数据根标记、仓库本地真测授权、固定场景和 `.bili-workspace-test-run.json` 分别承接产品数据根身份、当前仓库长期授权、UID/BV 目标和单次运行所有权，职责不同；长期授权不取消场景与通用运行所有权校验。

### 3.2 测试根与单次运行

- 继续通过 `BILI_TEST_ROOT` 向 `tools/t_project_isolation.py` 传递最终测试根并创建仓库外直接子运行；自动入口由仓库本地授权的 `test_root` 注入该环境变量，显式入口仍由调用者设置。
- Windows 显式真链入口要求调用者设置绝对 `BILI_TEST_ROOT`；自动入口使用仓库本地授权中绑定的绝对 `test_root`。两者都不能回退到通常位于 `%LOCALAPPDATA%` 的系统临时目录。
- 测试根不得与源码仓库或凭据源互相包含，不得是符号链接或重解析点；run 内的配置、数据库、下载、缓存、日志、浏览器 profile、临时文件和工具均不得越界。显式 UNC 路径仍须通过相同的可写性、空间与 containment 检查，不因位置类型自动获得信任。
- `summary.json` 从创建时即记录 `test_id=T-BILIBILI-LIVE` 和运行身份，使中断运行仍可与普通 `T-PROJECT` run 区分；通用所有权标记格式不为本套件分叉。

### 3.3 凭据与工具

- 只把源端普通文件 `config/bbdown/BBDown.data` 复制到隔离产品数据根 `run/runtime/config/bbdown/BBDown.data`，不解析、不输出、不摘要、不比较内容，也不把它复制到共享缓存。
- BBDown 会在调用前把凭据镜像到自身可执行文件目录；因此源码和候选目标都先把工具放进本次 run。成功退出时在产品停止后删除 run 内所有精确 `BBDown.data` 副本，失败时按维护者选择保留整个 run。
- 源码目标需要真实下载时，默认使用仓库中当前正式 EXE 作为工具提供者：先核对 `launcher/current-build.json` 的文件名、大小与 SHA-256，把 EXE 复制到 run 后执行 `--self-check`，再使用它在 run 内展开且已校验的 BBDown/FFmpeg。只读发现不强制准备下载工具；原 EXE、原控制根和正式构建记录不被修改。
- 可显式提供另一个带匹配构建记录的启动器作为工具提供者；身份不完整或工具自检失败时为 `blocked`。入口不联网获取工具，也不因应用源码变化要求重新打包。

## 4. 套件选择与执行顺序

### 4.1 影响域

以下变化选择只读真实链：Bilibili 登录状态、Cookie 适配、WBI、关键词或 UP 主搜索、资料、投稿、封面、元数据和直接消费这些返回的页面。

以下变化在只读链之外增加有界下载：BBDown/FFmpeg 适配、画质预检、下载、严格批量提交、任务队列、全量入库、索引入库、作品库、概览作品入口或播放链。

前端相关页面受影响时增加真实浏览器步骤；只改后端时直接走 HTTP API。启动器、冻结资源、内嵌 Web 或工具布局受影响时，除当前源码外增加临时候选 EXE 目标。

### 4.2 固定顺序

1. 先运行仓库授权、固定场景、路径、工具、fixture 和运行器的快速静态/模拟检查。
2. 选择条件满足且环境有效时运行真实只读成功链；下载影响域再运行有界下载，前端影响域再运行浏览器观察。
3. 真实链得到 `passed` 后运行本次影响域模拟测试；真实链为 `failed`、`blocked` 或 `inconclusive` 时停止后续昂贵阶段并交接实际原因。
4. 共享认证、持久化、任务队列、公共 API、前端运行时或影响无法可靠界定时，最终扩大为完整 `T-PROJECT`。
5. commit 或 push 前重新按当前候选与影响判断；旧结果不替代代码、fixture、仓库授权、固定场景、登录或环境变化后的验证。

新 Windows PowerShell 入口只负责 `T-BILIBILI-LIVE`，使用 PATH 中的 PowerShell 7；自动模式让 Python 编排器读取仓库本地绑定，显式模式传递调用者给定的凭据源与 `BILI_TEST_ROOT`，两者都传递影响域和执行目标。它不并入 CI，也不让通用 `verify-source.sh` 自动触碰真实环境。

## 5. 真实成功链

### 5.1 发现与目标验证

- 用包装现有 `httpx.Client` 的记录客户端调用当前 `app.search`、`app.metadata` 适配函数，在不代理、不记录请求头的前提下取得公开响应正文；`/nav` 只供代码提取 WBI 和登录结论，原始正文不落盘。
- 真实解析指定 UID 的资料和全部必要投稿页，验证 8 个 BV 均属于同一 UID，并取得标题、时长、封面与分页事实。任一目标不存在、不可读或归属不符时整体 `blocked`，不联网替换。
- 请求头、Cookie、二维码载荷、原始 `/nav` 账号响应、WBI 签名查询值和响应头均不得进入记录。公开正文只保存在仓库外 run。

### 5.2 有界批量下载

- 在隔离应用中建立一次性本地管理员会话，不复用真实网站账号、浏览器会话、数据库或用户 profile；一次性密码和 CSRF 值不写入摘要。
- 把 8 个已验证作品交给现有 `/api/download/selection` 严格批量入口，下载并发固定为 1，按固定场景顺序观察任务。
- 至少一个作品完整下载、质量复核、索引入库并能读取详情，才形成下载成功证据；随后继续到 8 个，或 15 分钟、run 增长 2 GiB 任一上限先到。开始前可用空间少于 5 GiB 时不进入下载。
- 每项开始前结合真实时长与 BBDown 信息预检剩余预算；运行中监控 run 增长和总耗时。上限到达后通过 API 取消尚未完成任务，等待自有进程退出，不按名称结束系统进程。
- 已有至少一个成功项时，上限导致的其余取消不改变整体成功，但摘要必须记录请求数、完成数、取消数和停止原因；一个也未完成时为 `inconclusive`，除非已有可判定的产品失败。

### 5.3 浏览器与作品入口

- 复用现有浏览器探测，只连接测试拥有的回环服务，不复用用户 profile，不下载浏览器。
- 验证 UID 搜索、UP 主资料、投稿分页、真实封面加载和跨页选择；打开“UP 主全量入库”确认框后取消，不启动无界作业，再以 8 个固定 BV 点击严格批量下载。
- 至少一个作品入库后，从概览最近作品卡通过鼠标和键盘分别进入对应作品详情；播放受影响时再验证实际媒体可打开与 Range，不扩大到完整观看。
- 浏览器缺失、真实封面受上游或网络阻断时按环境事实记为 `blocked`；页面路由、按钮、封面处理或作品详情合同错误记为 `failed`。

### 5.4 候选 EXE

- 在启动器内部增加仅供已验证测试 run 使用的隐藏 live-session 入口，复用 runtime smoke 的资源、数据根锁、健康探测、唯一端口、后端句柄和优雅停止能力；不开放普通用户配置项，不接受凭据源路径。
- 外部编排器只把已验证候选复制进 run，候选只读取 run 内数据根和凭据，写出位于同一 run 的就绪/结束记录并等待精确停止信号。API 与浏览器步骤由外部编排器复用，不在启动器里复制业务断言。
- 原有 `--runtime-smoke`、候选构建和正式快照行为保持不变。live-session 的路径、令牌、超时、进程所有权和异常停止须有启动器单元测试。

## 6. 真实响应与模拟 fixture

### 6.1 记录和清洗

- 只记录本次影响域实际使用的公开搜索、UP 主资料、投稿和作品详情 JSON；原始文件位于 `results/raw-public/`，不进入 Git。
- 清洗器遍历完整 JSON，保留所有非动态字段名、嵌套、标量类型、空值和每种数组元素结构；真实 UID、BV、昵称、简介、标题、图片路径、时间、统计、签名及其他易变值换成确定、类型有效的占位值。若真实身份或内容本身被用作字段名，则安全停止，不把该动态键带入候选。
- 跟踪的结构 fixture 位于 `SoftwareTesting/bilibili_live/fixtures/`，不得包含从原始正文逐字复制的真实身份或内容。现有行为测试可以从清洗 fixture 构造成功路径，失败、权限、竞态和异常仍使用最小人工变体。
- 清洗器必须确定性、幂等；相同结构不同真实值生成相同候选。对未知字段也保留键和类型，不能因未在允许列表中而静默丢弃。

### 6.2 漂移与刷新

- 正常真测只读比较当前结构与已跟踪 fixture，绝不修改仓库。没有漂移且产品行为通过时可以继续；结构变化但产品仍可用时结果为 `inconclusive`，并在 `results/fixture-candidate/` 生成候选和差异摘要。
- 首次实现尚无真实结构基线时按结构漂移处理：只运行 discovery 并生成候选，不进入下载或浏览器等昂贵阶段；显式刷新并通过模拟测试后，再重跑 discovery 和本次其余影响域。后续漂移沿用同一停点，避免先下载再因 fixture 变化重复执行。
- 结构变化已导致搜索、封面、下载或其他合同错误时为 `failed`。新增未消费字段也必须 review，但不冒充产品故障。
- 独立 fixture 刷新命令只接受一个已验证 `T-BILIBILI-LIVE` run 中的清洗候选，重新执行禁止值、路径和结构校验后才写入跟踪目录。它需要明确修改授权，不自动 commit 或 push。
- 刷新后必须 review 差异并运行适配器和消费页面的模拟测试，再重新执行真链；不能用自动覆盖后的绿灯替代对上游变化的判断。

## 7. 结果、保留与人工清理

### 7.1 结果文件

`results/summary.json` 使用短期 schema，至少记录：schema 版本、`T-BILIBILI-LIVE`、run ID、开始/结束时间、影响域、源码提交与脏状态或候选 build 身份、工具提供者身份、UID/BV、阶段状态、实际完成数、资源使用、fixture 漂移和安全错误分类。它不记录凭据源路径、Cookie、请求/响应头、本地管理员秘密、CSRF、WBI 值或原始异常对象。

状态遵循现有协议：

- `passed`：本次必需真实阶段均可判定成功；有界下载至少完成一项。
- `failed`：已经进入检查且产品行为或已声明合同错误。
- `blocked`：授权、登录、网络、风控、浏览器、工具、磁盘或固定目标不足，尚未形成产品判断。
- `inconclusive`：结构漂移待审查、运行中断、上限前没有完成下载、运行器异常或必需阶段被跳过。
- `not_run`：影响未命中，或仓库本地授权与逐次显式授权均不存在，套件未执行。

### 7.2 保留和删除

- 成功运行在停止应用和自有子进程后删除全部凭据副本，保留公开响应、清洗候选、摘要、日志和下载结果。
- 失败、阻断或不可判定运行保留整个 run，包括其中的凭据副本；日志和摘要仍必须脱敏。任何能读取测试根的人可能读取该 Cookie，这是维护者已接受的残余风险。
- 不做退出自动清理、启动时 GC、后台清理或计划任务。运行创建满 72 小时只表示具备人工清理资格，不保证届时自动消失。
- 只读命令可以列出已验证为 `T-BILIBILI-LIVE` 且超过 72 小时的精确 run。维护者明确指定删除后，逐个重新验证通用所有权标记、summary 身份、直接父子关系、年龄、重解析点和仓库/凭据源 containment，再调用精确单 run 删除；不删除测试根或相邻内容。

## 9. 验证顺序

1. 运行新增仓库授权、固定场景、路径、清洗、摘要、预算、凭据清理、进程和 candidate live-session 的聚焦模拟测试；测试使用虚构 Cookie 和本地假服务。
2. 运行受影响 Python、Launcher 与源码边界检查，确认普通 pytest、T-PROJECT 和 CI 不会选择真实套件，固定场景及原始响应不能被跟踪，仓库授权只位于 Git common directory。
3. 在另行取得完整测试授权后运行完整 `T-PROJECT`；运行 T-DOC 与 `git diff --check`。归档输入只在最终关闭时变化，届时运行一次 T-ARCHIVE。
4. 在维护者已明确要求创建有效仓库本地授权并准备固定场景后，该授权绑定凭据源与安全测试根，持续授权方案内的产品启动、真实网络和有界下载，无需逐次重复询问；先运行源码 discovery。首次无基线或发生结构漂移时在此停止并生成候选，只核对获准读取的场景与凭据文件在运行前后类型、大小和修改时间未变化，不枚举凭据源其余目录。
5. 若生成 fixture 候选，在明确刷新授权后写回、review 并运行消费它的模拟测试；随后重新执行源码 discovery，只有结构一致后才继续 download 和 browser，避免重复媒体下载。
6. 因本方案需要增加 candidate live-session，另行取得候选构建授权后运行 `T-LAUNCHER` 聚焦测试和临时候选构建，把候选 EXE 与 candidate 记录复制进 live run 并核对身份后执行同一真链。成功构建 staging 按 T-LAUNCHER 既有所有权规则精确清理，live run 中的候选副本随其他诊断产物保留；失败 staging 沿用 T-LAUNCHER 的失败诊断边界。任何候选都不晋升或覆盖正式 EXE。

## 10. 完成与停止条件

只有以下条件全部满足，才可关闭待办：

- 新套件只能由有效仓库本地授权加固定场景选择，或由调用者逐次显式提供两个根；运行器不能自授权、扫描或修改凭据源，普通测试仍完全使用虚构数据。
- 源码目标在真实登录下完成公开接口、同 UID 八项校验、真实封面、至少一项下载/质量复核/入库、概览详情入口和受影响浏览器步骤。
- 候选 live-session、路径和进程所有权由模拟测试证明；临时候选在真实链中得到可判定结果，正式 EXE 与规范构建记录未变化。
- 自动结构候选保留未知字段与类型且不含真实身份、内容或秘密；漂移、刷新和重新验证形成闭环。
- 时间、增长、空间、数量、停止、凭据成功清除、失败保留和人工精确清理行为均有测试；交接明确列出实际保留 run。
- 完整项目回归、受影响启动器验证、文档门禁和差异检查均得到可判定结果；长期文档与实现一致。
- 完成后从活动待办移除本项，把方案移动至归档并更新归档索引；这些关闭动作不包含 Git 交付。

遇到以下任一情况停止并申请差额授权或新决策：

- 没有可用凭据源、同一 UID 的 8 个较短既有 BV、显式仓库外测试根、已校验工具、浏览器或候选构建能力。
- 需要读取凭据源其他文件、把真实值写入仓库、安装或下载依赖/工具、访问 CI secret、建立自动清理、突破 15 分钟或 2 GiB 上限。
- 候选真实测试只能通过开放通用后端入口、复用用户数据根、控制现有进程或改变启动器正常 GUI/运行合同实现。
- Bilibili 登录、网络、风控、目标可用性或响应漂移使结果只能为 `blocked` 或 `inconclusive`，且没有已确认的安全替代。
- 目标文件与用户既有改动冲突，或实现需要修改全量入库、严格批量提交、数据库 schema、权限或其他产品语义。
- 需要正式打包快照、提交、推送、PR、发布或删除尚未取得精确授权的仓库外运行目录。

## 11. 方案 Review（2026-09-02）

| 维度 | 结论 | 处置与剩余风险 |
| --- | --- | --- |
| 独立套件必要性 | 通过 | 真实账号、网络、BBDown 和媒体副作用与 T-PROJECT 的虚构/离线职责不同，单独登记 `affected_only`，不放宽普通测试 |
| 授权是否自洽 | 通过 | Git common directory 本地文件形成仓库窄授权并绑定凭据源与测试根；固定场景只提供 UID/BV，运行器不能创建二者或扫描数据根 |
| 持续授权边界 | 通过 | 仓库本地授权必须由维护者明确要求创建；有效文件随后覆盖本方案内的逐次真链运行，不重复询问，也不授权候选构建、fixture 写回、清理或 Git 操作 |
| UID 来源可实现性 | 通过 | 现有下载记录没有 creator UID；固定场景创建动作在单独授权下读取必要 BV/时长并用公开作品详情解析 `owner.mid`，运行器不承担该扫描 |
| 本地文件职责 | 通过 | 仓库本地文件承接授权与环境定位；`.bili-workspace-live-test.json` 承接固定目标；通用 run 标记和摘要只证明单次目录归属 |
| 测试根复用 | 通过 | 自动入口从仓库授权取得绑定测试根，显式入口继续使用 `BILI_TEST_ROOT`；两者复用同一 containment 并拒绝 `%LOCALAPPDATA%` |
| 源码工具来源 | 通过 | 复制并自检既有正式启动器后只使用 run 内工具，避免每次源码改动重新打包，也避免凭据写入共享资源目录 |
| 候选 EXE 可测性 | 通过但实施风险较高 | 隐藏 live-session 只负责受控启动与停止，业务断言仍由外部编排器拥有；若路径保护无法在不开放通用入口的前提下成立则停止 |
| 候选产物所有权 | 通过 | live run 保留已核对的候选与记录副本，原构建 staging 按 T-LAUNCHER 规则处理，不把“人工清理三天外 live run”扩大到构建目录 |
| 八项抽测与硬上限 | 通过 | 八项是尝试上限而非通过数量；至少一项成功证明下载链，时间/增长先到即取消并如实记录，因此不会为凑数突破资源线 |
| 全量入库覆盖 | 通过 | 真实链明确不启动无界作业，只验证同一外部发现层和严格批量下载；全量调度生命周期由模拟测试承担，不虚报真实覆盖 |
| 自动 fixture | 通过 | 完整结构自动生成避免人工最小样本漏项；普通运行不改仓库，显式刷新、review 和重跑避免自动接受破坏性漂移 |
| 首次基线与重复下载 | 通过 | 首次缺少 fixture 或后续漂移都在 discovery 后停止；先刷新并跑模拟测试，再进入下载和浏览器阶段，不为建立基线重复下载媒体 |
| 敏感信息 | 通过但有已接受残余风险 | 不采集请求头、账号响应或 Cookie 内容；失败 run 可保留凭据且不会自动过期，访问测试根的人可能读取，交付必须明确路径和人工清理责任 |
| 凭据源只读证明 | 通过 | 自动入口只解析数据根身份标记，运行器只解析固定场景并复制固定凭据；运行前后只比较场景与凭据的类型、大小和修改时间，不为证明未修改而扫描其余真实目录 |
| 结果语义 | 通过 | 产品错误、环境阻断、结构待审和未运行分开；兼容漂移不得以 warning 冒充通过 |
| Git 与发布边界 | 通过 | 原始响应和固定场景永不进 Git，仓库授权只位于 Git common directory；fixture 仅能显式清洗刷新，候选不晋升，方案不含 commit、push 或发布授权 |

Review 未发现仍需维护者作新的产品或安全选择。实施前只需取得本方案范围的修改授权；完整测试与候选构建仍需相应明确授权。真实凭据、网络、产品进程和有界媒体下载由维护者明确要求创建的有效仓库本地授权持续覆盖，不逐次重复询问；fixture 写回、仓库外删除和 Git 交付仍须在实际发生前另行取得授权。
